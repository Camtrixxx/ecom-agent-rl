# #28 · 六份权重同窗口重评

## 要拆的东西

3 对 3 的已发布结果是 **+3.06 pp [+0.43, +5.70]**，六份权重的评测时刻却是散的：

| 组 | 权重 | 已发布成功率 | 评测时刻 |
|---|---|---|---|
| v1 | `sft` | 0.6061 | **08-11 18:12** |
| v1 | `sft_s43` | 0.6243 | 08-14 14:24 |
| v1 | `sft_s44` | 0.6288 | 08-14 18:38 |
| v2 | `sft_v2` | **0.6626** | 08-14 03:58 |
| v2 | `sft_v2_s43` | 0.6406 | 08-14 16:19 |
| v2 | `sft_v2_s44` | 0.6479 | 08-14 18:38 |

于是 +3.06 pp 里混着两个东西：**种子运气**（每份权重的训练 run 方差）和**评测漂移**（不同
时刻评同一份权重会差 ~2 pp，见 roadmap 阶段 C）。已发布的区间只覆盖每题采样噪声，两者都
不在里面。

**六份权重放进同一个窗口重评一次，漂移项就被压到窗口内水平（实测 0.39 pp，见 #14 的锚）。**
剩下的就是种子运气，那正是 3 对 3 想量的东西。

## 设计与已知代价

九条腿的配置逐字相同：`data/task_pools/evaluation.jsonl` 500 题、k=4、温度 0.7、
concurrency 16、`hash_environment.py` 闸门、兜底重解析计数须为 0。差别只有权重。

六条腿**并行**跑（GPU 1-6，vLLM 端口 8180-8185，环境段 5700/5800/5900/6000/6100/6200），
这样窗口跨度压到最小（约 1 h）而不是串行的 4.5 h。

**代价，认了但要记**：六条腿互为彼此的机器负载，而负载正是漂移的嫌疑机制之一（#27 要查的
就是它）。所以这个窗口的"负载环境"和任何单腿评测都不同。**这不影响 #28 的主判定**——主判定
是六个数**互相之间**的比较，六条腿共享同一个负载环境；它只影响"新值对已发布值"的差
（次判定），那个差里因此含一项"六并行 vs 单腿"的未知偏置。次判定的结论要带这句限定。

GPU 0 上有别人的常驻服务（~8 GB），**不排任何工作到 GPU 0**。

## 主判定：窗口内的 3 对 3

D_W = mean(v2 三个新值) − mean(v1 三个新值)，两样本 t、合并 sd、df = 4、**t₄,₀.₉₇₅ = 2.776**。

- **D_W 区间不跨 0 且 D_W 与 +3.06 pp 相差 ≤ 1 pp** → 3 对 3 扛住了窗口控制，"v2 配方约有
  3 pp 收益"这句话站得住，已发布的点估计可以继续引用。
- **D_W 区间跨 0** → 3 对 3 对窗口不稳健，降级成**测不出**。roadmap 里那一节的措辞要从
  "涨 3.06 pp"改成"测不出"，并写明是被 #28 降级的。
- **D_W 与 +3.06 pp 相差 > 2 pp**（不论符号）→ 已发布那个差值被窗口严重污染。**以新值为准**，
  并把差额记成"整组错开的窗口偏置"的第二次直接测量（第一次是 #14 的 +0.91 pp）。

注意 D_W **含双侧训练 run 方差**（六份权重是六次真实训练），这一点和 #14 的同窗口锚相反
（那三份锚是同一份权重重评三次）。所以 D_W 的区间会比 #14 宽，那是对的，不是设计缺陷。

## 次判定：0.6626 到底高不高

roadmap 阶段 C 记了一条**具体的头条数字嫌疑**：已发布的 `sft_v2` = 0.6626 比它后来两次重评
（0.6401 / 0.6462，彼此只差 0.43 pp）的均值高 **1.94 pp**，而它正是 SFT 侧 +5.42 pp 的被减数。
n=1 对 n=2 定不了案。这条臂把它变成 n=6。

记 δᵢ = 新值 − 已发布值（六份权重各一个），δ̄ = 六个 δ 的均值。δ̄ 吸收"整个窗口相对 08-14
的公共位移"，所以要看的是 **`sft_v2` 偏离 δ̄ 多少**，不是 δ 本身。

- **δ(`sft_v2`) − δ̄ ≤ −1.5 pp** → 嫌疑**成立**：0.6626 是个偏高的离群值。那么 SFT 侧
  +5.42 pp 应下修到 +3.5 pp 量级，和 3 对 3 的 +3.06 pp 一致。
- **|δ(`sft_v2`) − δ̄| ≤ 1.0 pp** → 嫌疑**被否**：0.6626 不比别的数更可疑，1.94 pp 那个观测
  是两次重评自己偏低（或纯噪声）。要在 roadmap 里删掉"有偏高嫌疑"那段并说明是被 #28 否掉的。
- 落在 −1.5 与 −1.0 之间 → **不定**，照登，不改任何措辞。

**`sft` 要单独看**：它是 08-11 评的，间隔约 5 天，其余五份约 2 天。按"漂移是间隔的函数"
（roadmap 阶段 C），它的 δ 不该和另五个同池。所以 **δ̄ 报两个版本：含 `sft` 和不含 `sft`**，
判定用**不含**的那个（五份权重同为 ~2 天间隔），含 `sft` 的版本只作参考。这条现在定，
不等看完数再挑。

## 附带产出（不作判定，但必须记）

六个 δ 的标准差 = **六份不同权重、约 2 天间隔的漂移量级**，是本项目最好的一次漂移估计
（此前最好的是同一份权重重评三次：窗口内 s = 0.39 pp）。它回答一个 #14 答不了的问题：
漂移是不是权重无关的公共位移。若六个 δ 紧紧聚在一起（s < 0.7 pp），漂移就主要是**公共位移**，
那么同窗口配对能几乎完全消掉它；若散开到 1.5 pp 以上，漂移带**权重相关**的分量，同窗口
配对也只能消掉一部分——这会直接影响所有已发布配对差的可信度，要在 roadmap 里写清。

## 顺带白捡的一条：步数效应从「排除法」变成近似同窗口的 3 对 3

**05:05 补，六条腿在跑、一个新数都没有，所以这条也是盲的。**

#14 收尾时记了一句限定：步数效应（v1@81 步 → v1@102 步）**只有软估计**，因为它是拿
stepmatch 三 seed（08-15/16 评）对已发布的 `sft` = 0.6061（**08-11** 评）比出来的 +3.79 pp，
跨天带 ~2 pp 漂移；"+5.42 pp 主要是步数"因此是**排除法**结论，不是直接测量。当时记的补救
办法是"再跑一条 v1@81 步的同窗口臂，约 2.3 h"。

**#28 把这条臂白送了**：它重评的 `dw_sft` / `dw_sft_s43` / `dw_sft_s44` 正是 **v1 数据 @81 步
的三个 seed**，全在 08-16 05:00 这一个窗口里。而 v1 数据 @102 步的三个 seed（`sft_stepmatch_*`）
评于 08-15 20:40 / 23:50 和 08-16 03:08。于是：

    步数效应 = mean(stepmatch 三 seed) − mean(dw_sft 三 seed)
             = v1@102 步  −  v1@81 步        ← 两侧都是 v1 数据，只差步数

所以**不再排期那条 2.3 h 的臂**，省下的机时留给别的。

**这是探索性分析，不是预注册判定**，理由有两条，都要跟着这个数一起引用：

1. **两组的窗口不同**（05:00 对 20:40–03:08），间隔 2–8 h。按"漂移是间隔的函数"，这个区间
   落在"几小时内 ±1 pp"那一档而**不是** ≥40 h 那一档，所以比先前的 08-11 对 08-15 好得多，
   但仍**不是**同窗口。
2. **没有预设阈值**。我不在这里写"若 > X pp 则如何"，因为我想不出一个在看到数之前就有道理的
   阈值——步数效应的先验只有"应该是正的、量级几个 pp"。硬编一个阈值反而是假装严格。

所以它的用法只有一个：**把 #14 那句"按排除法"改成"有一个近似同窗口的直接估计，量级 X pp"**，
并保留"两组窗口相差 2–8 h"这句限定。它**不能**用来推翻或确认 #14 的主判定（那条判的是数据
效应，和步数效应是两个不同的量）。

由 `scripts/analyze_dayeval.py` 在主判定之后一并打印，标着"探索性"。

## 假设

roadmap 阶段 C 写着一个**未验证**的机制假设：跨 session 漂移来自"连续批处理下批构成随 机器
负载变化"。共用机器，负载不可控，所以拿 `--concurrency` 当自变量去代理批构成。

## 设计

同一份权重 `outputs/models/sft_v2`，同窗口三条并行腿，**只有 concurrency 不同**：
c = 8 / 16 / 32（GPU 1-3，端口 8180-8182，段 5700/5800/5900）。c=16 那条是口径基准，
另两条各差 2 倍。

## 必须同时量的东西：实际批大小

**这是这条臂能不能解读的关键。** 环境侧每段只有 8 个 GIL 绑死的 worker（约 4-5 ep/s 各），
所以 c=32 时大部分 rollout 线程可能在等环境而不在等 LLM——**concurrency 翻 4 倍不等于 vLLM
的在飞批大小翻 4 倍**。若三条腿的实际批大小差不多，那这条臂根本没操纵成自变量。

所以从 `outputs/logs/vllm_*.log` 里抽 vLLM 自己打的在飞请求数（`Running: N reqs`），
报每条腿的均值与 p90。**先看它，再看成功率。**

## 判读分支

设三条腿两两之间的配对差（同 495+ 题配对，bootstrap 95%）。

- **先看自变量有没有被操纵成**：若 c=32 的实际批大小均值 **不足** c=8 的 2 倍 → 记成
  **"没能操纵自变量"**，不是"假设被否"。补救办法是加环境 worker 数（每段 8 → 32）再来，
  或换用直接控制 vLLM `--max-num-seqs` 的做法。这一支要老实写，不能拿它当阴性结果用。
- 自变量操纵成立的前提下：
  - **任一对的 95% 配对区间不跨 0** → concurrency 可测地改变成功率。**结论：评测口径必须
    钉住 concurrency**（现在是钉住的，16，所以已发布结果内部一致，但这解释了漂移的一部分），
    批构成是漂移的活机制。
  - **三对区间全跨 0 且极差 ≤ 1 pp** → 批构成**解释不了**那 2 pp 的跨天漂移。要去别处找：
    候选是 vLLM/驱动的非确定性归约顺序、环境侧状态、以及"根本没有机制、只是配对区间本身
    比它声称的窄"。这一支要在 roadmap 里把那条机制假设标成**已检验、不成立**。
  - **区间跨 0 但极差 > 1 pp** → 量级够大但 n 不够，记成"有信号、测不动"，并把极差记成
    漂移量级的又一次测量。

## 一个不打算修的限制

三条腿并行，所以它们互为彼此的负载；而 c=32 那条会先跑完，之后另两条的环境负载就变了。
共用机器上这件事修不掉（串行跑会引入跨窗口漂移，比这个更糟）。这条臂因此测的是**"评测自己
的 concurrency"**，不是"机器总负载"。后者要真测得另找办法，不在本次范围。
