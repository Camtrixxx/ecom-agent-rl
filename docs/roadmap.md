# Roadmap

## 已锁定的决策

| 项 | 决定 | 说明 |
|---|---|---|
| 主线 | Baseline → SFT → GRPO → Evaluation | 沿用参考实现的四阶段，不加新阶段 |
| 模型 | Qwen2.5-7B-Instruct | 纯文本；Qwen3.5 全系列是多模态，vision tower 于本任务无用 |
| 数据 | SFT 3,000/500，GRPO 3,000/200，评测 500 | 一律指**任务池的任务数**，不是 accepted 轨迹数；见阶段 B |
| 训练 | 8 卡原生，不 offload | 参考实现的单卡妥协在 80G 卡上纯属速度损失 |
| 环境 | 复制到 `third_party/`，不入 git，但有内容锚 | 上游没有 v2.1，必须带下游实现；锚见阶段 A |
| 参考实现 | `/data/heyuhang/shopping-grpo-longhorizon` 只读 | 唯一对照基准，不在其上改动 |

硬件：8 × A800-SXM4-80GB（640G 显存），driver 570.172.08，`/data` 可用 980G。

模型权重：`/data/heyuhang/models/Qwen2.5-7B-Instruct`（7.6G）。

后续 scaling 对照可用同系列 Qwen2.5-14B/32B-Instruct，tokenizer 与 chat
template 一致，适配层无需改动。

## 实施顺序

原则：先有可信评测和足量数据，再训练。否则训练结果无法解读。

### 阶段 A — 环境服务与容量基线

参考实现是单 Flask `app.run()` 进程、`SHOPSIM_ENV_SLOTS` 默认 8。rollout 并发、
评测并发、教师采集并发吃同一个 slot 池，这是全项目的吞吐上限。

- [x] setup 脚本：装环境依赖（独立 py3.10 venv）+ 校验商品数据 SHA-256 + 建索引
- [x] 容量压测：slot 开到 8/32/64/128，测 QPS 与 p99，找单进程饱和点
- [x] 若单进程不够：多进程环境服务 + 负载均衡
- [x] 记录容量 SLO，作为后续所有并发配置的输入

结论与原计划的假设相反：**加 slot 不提升吞吐**。单进程被 GIL 锁死在 1 核、
~4-5 episodes/s，并发 1 即饱和，8 slot 与 32 slot 在吞吐上没有区别。扩展只能靠
多进程，且到 32 进程仍是线性（133 ep/s）。最优工作点是并发 = worker 数。
详见 [environment-notes.md](environment-notes.md)。

所有 env 共享同一个 server 实例，商品库只加载一次，因此加 slot 主要吃会话状态
而非 20M 商品库副本；单进程的限制来自 GIL。

商品数据 SHA-256：`57b10950a0064d16c81535a1d764a75879a508d250dde8a2a1787c5e6045559f`

环境**代码**内容锚（46 个文件，`data/environment/manifest.json`）：
`734d7100472682f49956f4d1b21ed097cf2a2335dff77d538ef3d0f324bae613`。补这个锚的理由是
商品数据有把关而评分器代码没有——`third_party/` 不入 git，`reward.py` 或
`configs/environment.json` 的权重改一行，本仓库全部数字静默失去可复现性且无人会知道。
`python scripts/hash_environment.py` 校验，闸门接在 setup / 起服务 / 训练 / 评测四处；
`SHOP_ENV_CONFIG` 指到锚外会被 `start_environment.sh` 拒绝（那是唯一能绕过锚的口子）。
详见 [environment-notes.md](environment-notes.md#环境代码是评分器所以它需要一个内容锚)。

### 阶段 B — 数据层

- [x] 任务池抽样扩到 SFT 3,000/500 + GRPO 3,000/200 + 评测 500
- [x] 三者 task_id 零重叠，sha256 + provenance 血缘记录
- [x] 按 `attributes` 数量分层记录，用于分层报告
- [x] 教师轨迹采集：断点续跑 + 并发（并发上限受阶段 A 的 SLO 约束）

切分共 7,200 条（占全池 30.7%），分层轴是 `domain_en_short` × `attributes` 桶。
各池难度分布与全池的偏差在 1 个百分点内，9 个品类全覆盖；grpo_val 只有 200 条，
抽样噪声最大（5-7 桶 39.0% vs 全池 35.9%），分层报告解读时要留意。
`python scripts/build_task_pools.py` 复现，血缘见 `data/task_pools/metadata.json`。

数量口径（此前本节勾选项写「任务池 3,000/500」而正文写「3,000 条 accepted」，两处
混用，现锁定）：**「3,000/500」指任务池的任务数。** 采集按 1 任务 1 轨迹，所以 SFT
数据集的行数 = 3,000 × 接受率，不是 3,000。

实测：3,000 条原始轨迹 → **1,781 条 accepted**（接受率 0.5937），held-out 的 500
任务池 → **299 条 accepted**。这就是阶段 B 的交付物，落在 `data/sft/` 与
`data/sft_val/`，血缘见各自 `metadata.json`。接受标准是 `gold_purchase` +
`valid_alternative_purchase`，被拒步数上限 3。

接受率不能和参考实现直接比：它 0.4107（2,498 → 1,026）里最大的丢弃项是
`guard_violation` 716 条，占其原始轨迹 28.7%，而本项目对应的格式类丢弃只有
`dropped_tool_calls` 80 + `has_error` 93；教师模型也不同（它用 deepseek-v4-flash）。
差值主要来自丢弃口径与教师，不是数据质量。

另一处结构差异，会影响 val 能有多大：参考实现的 validation 从同一批 1,026 条
accepted 里按 `exact_rows` 切 200 条，**SFT train 与 val 共享任务**；本项目的 val
来自独立 held-out 的 500 任务池，任务零重叠。代价是 val 行数被接受率封顶——500 个
任务、接受率 0.598，299 条已经是天花板。想要更多 val 只能扩任务池，多采样没用
（同任务重复采样不能当独立验证样本）。

若日后改成把 accepted 行数本身当目标（例如 3,000 条 train），按实测 0.5937 反推需
约 5,050 条原始轨迹，即对现有 3,000 任务池每任务采 ~1.7 次，需换 seed 并按轨迹去重。
届时要留意：同任务的多条轨迹进同一个训练集会放大该任务的权重。

### 阶段 C — 评测

- [x] 并行 rollout（参考实现是 `for task in tasks` 串行）
- [x] 每题 k 次采样 + 置信区间
- [x] 按 task_id 配对比较
- [x] 按 `attributes` 数量与品类分层报告
- [x] 评测隔离：移除 reward、gold、raw observation
- [x] Baseline 跑通，作为对照下界

隔离做在 rollout 层而不是评测层：`observation.split_env_payload` 用白名单过滤，答案
字段在**写盘之前**就被剥离到 `audit`，所以任何读轨迹文件的下游都拿不到 gold。参考
实现把 `goal`/`reward_detail` 原样存进 `terminal_result`，只在喂 Judge 时才过滤。

实测发现两处参考实现没提的泄漏：`goal_options` 在 reset 就给出目标商品规格；
`progress.credited_evidence_added` **每一步**都带 `constraint:<asin>:budget:fail`
这类逐条约束判定，等于把评分器交给模型。两者都已拦掉并有测试钉住。

指标层的三个决定（`evaluation/metrics.py`）：主指标是成功率而非平均 reward——后者会把
「买错了」（-0.85）和「没买」（-0.15）混成一个数，`wrong_purchase` 率单独报；置信区间
用 bootstrap 而非正态近似，成功率低到 0.1 时 Wald 下界会越界；每题 k 次采样先按题内
取平均再对题 bootstrap，否则 k×N 条被当独立样本、区间算窄。终局标签取
`audit.terminal.reward_detail.reward_type`（环境的权威判定），不从 messages 猜。
配对比较实测比非配对区间紧（0.0530 vs 0.0580），因为消掉了题目难度的方差。
`python scripts/report_metrics.py --trajectories <轨迹> --pool <池> --baseline <对照>`。

拿真轨迹验指标层时发现一个自己的 bug：`run_batch` 把基础设施失败（env_error 等）也写进
主轨迹文件，于是续跑按 `(task_id, attempt)` 去重时永远跳过它们——「修好之后重跑即可续跑」
是空话——而指标层会把 `no_terminal:env_error` 当成模型的失败算进分布。现在这类失败改写
同名的 `.failures.jsonl`，留证据但不占用 attempt。`batch.py` 当时没有任何测试，这是它能
溜过去的原因；补了 23 个（`tests/test_batch.py`），其中 8 个会在退回旧行为时失败。

跑 baseline 前撞到一个必须先解决的问题：**35 步回合放不进上下文窗口**。实测 448 个
真实 observation，搜索结果页均值 2406 tokens（p90 2676），占全部 observation 开销的
91%；固定前缀 3494。按均值外推 35 步要 ~39k tokens，而窗口是 24576 —— **第 18 步就
撞 HTTP 400**，回合到此结束，前面的步数白跑。窗口开到模型上限 32768 也只推到第 25 步。

分两层解决。分类层：超上下文单独作 `ContextOverflowError` / `Status.CONTEXT_OVERFLOW`，
**不算** infra 失败——它和 `max_steps` 同类，是这道题的一个结局，算成 infra 会让一条长
回合掐掉整批采集。机制层：`rollout/context.py` 在发请求前压缩历史。

压缩策略与参考实现的关键差别：参考实现整组丢弃旧历史，而这会删掉「已经搜过哪些词」的
全部记录——`repeat_loop` 是 **−0.65**，专罚重复动作，于是压缩本身就在制造它要避免的
失败。这里删正文但留一条有界的动作摘要（超上限时丢最老的，防重复看的是最近做过什么）。
实测 35 步回合：未压缩峰值 39084，压缩后稳定在 ~21.6k，35 个查询全部仍可见。
7 个测试会在退回整组丢弃时失败。

配套的 `rollout/tokens.py` 必须和服务端算得一样——数少了照样撞 400，数多了白删历史。
两处反直觉的开销：chat template 的 `| tojson` 把中文工具 schema 转义成 `\uXXXX`，957 →
2818 tokens（**每请求多付 1861**）；`arguments` 是 JSON 字符串又被 tojson 二次序列化。
按真模板校准后偏差 1.55% 且偏高（安全方向：早压一点而不是撞墙）。
`python scripts/check_token_counter.py --trajectories <轨迹>` 可随时复核，换模型必跑。

Baseline 实测（500 题 × 4 次采样 = 2,000 条，Qwen2.5-7B-Instruct 原始权重）：
**成功率 0.0745 [0.0610, 0.0885]**，gold 率 0.0735，错买率 0.0060，平均 reward −0.0276，
平均被拒 1.63。轨迹在 `outputs/rollouts/baseline.jsonl`。

先跑的 k=1 给的是 0.0566 [0.0384, 0.0788]。**k=1 的点估计落在 k=4 区间之外**（0.0566 <
0.0610），反过来 k=4 的点估计仍在 k=1 区间内；区间宽度从 ±2.0pp 收到 ±1.4pp。两次用的是
同一批 500 题，差异纯来自题内采样噪声——这就是 k=1 不足以支撑「SFT 与 GRPO 差几个点」
这类比较的直接证据。

三点会影响后续解读：

**69% 的回合没走到购买**（`no_tool_call` 38.3% + `rejection_limit` 30.9%），主要瓶颈还不是
选品决策而是把动作发出去。拆开看是两种不同的失败，之前混在一起记成了一个数：

- **`<tool_call>` 块解析失败 7.1%**（142 条）：模型写了块，但里面混进垃圾
  （`ListItemIcon`、嵌套 `<|im_start|>assistant` 这类），hermes 对整块 `json.loads` 就失败。
- **动作写成自然语言 21.6%**（432 条）：压根没用块，直接写「动作: open_product("...")」。
  这不是解析器的问题，换任何 parser 都救不回来。

两者合计 28.7% 的回合里模型**已经选出了合法动作**，只是没能合法地发出去。报增益时必须
把这部分单独拆出来，否则「学会了正确输出格式」会被误读成「决策能力提升」。

**难度分层在这个能力水平上还没起作用**：四个桶 0.0489 ~ 0.0843，非单调（5-7 桶最高、
8+ 桶最低），CI 大幅重叠，且多数回合没走到约束满足那一步。等成功率上来再看这张表才有
意义——见阶段 D，SFT 之后这张表读出来的东西完全不同。

**错买率 0.0060 配 11.25% 的 `early_abstain`**：模型不是买错，是不敢买。RL 要推的是
「敢买且买对」，压低错买率不是目标（它已经接近 0）。

压缩在真实数据上确实被用到了：baseline 的 k=4 补采样三轮里触发 158 次，
`peak_original_tokens` 达 51493，是窗口 24576 的 2.1 倍——没有压缩层这些回合会直接撞
400，前面那节的分析被实测确认。（这批数只有批级计数，所以按批报；每回合计数是之后才加
的，重采之前不会有逐回合的数，见阶段 D 末尾。）

### 阶段 D — 训练

- [x] 8 卡分布式底座，SFT 与 GRPO 共用
- [x] 工具调用格式改为 `hermes`（参考实现用 `qwen3_coder`，非 Qwen2.5 格式）
- [x] 7B 全参 SFT
- [x] GRPO：不 offload，`gpu_memory_utilization` 0.85，group size 按实测放大到 8
- [ ] ablation 并行（每个并行实验需独立环境端口，否则互抢 slot）

SFT 实测（权重 `outputs/models/sft`，日志 `outputs/logs/sft_full.log`，血缘
`outputs/models/sft/metadata.json`）：FSDP2 全参 bf16，3 epoch / 81 optimizer step，
lr 1e-5、warmup 0.03、cosine 退到 0，grad_accum 4、32768 tokens/batch，耗时 1h41m。
渲染后 train 1,776 条 / val 298 条（分别丢 5 / 1 条，**全部因超 32768 长度**，无一条
因格式或边界问题被丢）。val loss 0.44066 → 0.39567 → **0.39249**。

实际跑的是 6 卡（GPU 2-7）不是 8 卡：GPU 0/1 当时被教师采集用的 vLLM 服务和其他进程
占着。FSDP2 配置本身与卡数无关，`world_size` 由 `accelerate launch` 决定，GRPO 复用
同一套底座时不需要改。

val loss 上第 3 个 epoch 只降 0.0032，而同期 train loss 从 ~0.36 掉到 ~0.31，过拟合的
起点已经出现。当时据此写过一句「第 3 个 epoch 几乎没有收益，下次可以省」——**这句话
后来被实测推翻了，别照它做**：省掉第 3 个 epoch 的常规做法（把 epochs 设成 2）会连带
把余弦计划压短，要付 6.71 pp。真正没有收益的是第 3 个 epoch **本身**（+0.85 pp，测不出）。
两者在 val loss 上分不开，见下面「[第 3 个 epoch 值不值](#第-3-个-epoch-值不值问的是-epoch起作用的是-lr-计划长度)」。
按 epoch 存 checkpoint 这件事已经做了，正是它让上面那笔分解成为可能。

训练链路上踩到两个坑，都在 `scripts/train_sft.py` 的注释里留了完整推导：**loss 的
fp32 上采必须分块**（vocab 152064 下 32k token 的 logits 整体 `.float()` 要 18.2G，
backward 里实测 "Tried to allocate 18.31 GiB" 而只剩 14.4G；`reduction="sum"` 对分块
求和满足结合律，等价）；**scheduler 不能交给 `accelerate.prepare` 包装**（它假定
batch 被乘了 `num_processes`，每 step 把内部计数推 6 步，于是 warmup 第一步就走完、
余弦半周期在 81/6≈13.5 步跑完后开始振荡，末尾 lr 回到 ~0.96e-5 等于完全没退火，
而日志里 loss 照样在降——这类 bug 不看 lr 曲线发现不了）。

**SFT 评测结果**（500 题 × 4 次 = 2,000 条，与 baseline 同池同 k，
`outputs/rollouts/sft.report.json`）：

| | baseline | SFT |
|---|---|---|
| 成功率 | 0.0745 [0.0610, 0.0885] | **0.6061 [0.5718, 0.6397]** |
| gold 率 | 0.0735 | 0.6046 |
| 错买率 | 0.0060 | 0.0544 |
| 平均 reward | −0.0276 | 0.4282 |
| 平均被拒次数 | 1.63 | 0.097 |

按 task_id 配对（498 题）：0.0748 → 0.6061，**差值 +0.5313 [+0.4967, +0.5617]**，
区间不跨 0。

阶段 C 要求把「学会格式」和「决策变好」拆开，否则前者会被误读成后者。成功率可以乘性
分解成「走到终局的比例 × 走到终局后买对的比例」：

| 因子 | baseline | SFT | 倍数 |
|---|---|---|---|
| 走到终局率 | 0.3080 | 0.9950 | ×3.23 |
| 条件买对率 | 0.2419 | 0.6065 | ×2.51 |

（两项相乘得 SFT 0.6035，比上表的 0.6061 略低：这里是按 2,000 条直接算的，主指标先按题内
取平均再对题 bootstrap，且剔掉了 24 条 reward 不可解析的轨迹。差 0.26pp，不影响结论。）

归因顺序会改变各自分到多少，所以两种都报：先记格式则 +16.6pp 然后 +36.3pp，先记决策则
+11.2pp 然后 +41.7pp。**两种顺序下决策项都是两位数**，所以增益不是「只学会了输出格式」。
配套证据：格式失败 28.7% → 0.15%（自然语言写动作 21.6% → 0），平均被拒 1.63 → 0.097。

分解与格式失败分类都由 `python scripts/decompose_success.py <对照> <待比较>` 复现，阶段 C
的 baseline 那两个格式失败数字出自同一个脚本。

三个值得记的行为变化：

**不敢买 → 敢买但会买错**，正是阶段 C 预判的那笔交易：`early_abstain` 11.25% → **0**，
错买率 0.0060 → 0.0544。RL 要推的是「敢买且买对」，现在错买率终于是个有意义的指标了。

**难度轴翻转了读法**：SFT 的成功率在四个难度桶上基本持平（0.5915 ~ 0.6377，无单调趋势），
但**错买率随难度单调上升**（0.0275 → 0.0533 → 0.0576 → 0.0996）。也就是说约束变多时模型
不是「做不到」而是「更容易买错」。阶段 C 那句「等成功率上来再看这张表」现在兑现了：瓶颈
从「发不出动作」移到了「约束核验」，这是 GRPO 该推的方向。

成功率那一行的「持平」要打个折扣：8+ 桶只有 46 题，CI 是 [0.5091, 0.7572]，宽到几乎放得下
任何趋势。单调上升的错买率是这张表里更硬的信号——它不依赖 8+ 桶那个点，去掉它剩下三档仍
单调。

**`repeat_loop` 的绝对数涨了但占比没恶化**：92 → 329 条（全体 4.6% → 16.5%），现在是
最大的失败类型。但它占**走到终局的回合**的比例是 14.9% → 16.5%，几乎没动——绝对数涨
是因为走到终局的回合本身多了 3.2 倍。把它读成「SFT 让模型更爱绕圈」是错的。

一条没有定论的线索。`repeat_loop` 的回合明显更长：SFT 里它步数中位数 18，而
`gold_purchase` 是 10（baseline 同向，10 vs 6）。压缩按均值大约在第 9-10 步开始生效，
所以绕圈的回合几乎都被压缩过，而买对的回合多数没有。压缩触发率也确实上去了——每次请求
3.29%（699/21256）对 baseline 的 1.61%（158/9828）。

但这**不足以说压缩在制造 `repeat_loop`**，有两条反向解释同样吃得下这些数：长回合本来就
更容易绕圈；而且 `repeat_loop` 按定义需要攒够重复动作才判得出来，短回合根本没机会被判成
它。三者都预测「绕圈回合更长、被压缩更多」。

做等步数对照缺的那件测量手段现在补上了：轨迹顶层多了 `usage`，记这一个回合自己的
token 与压缩次数（`compactions` / `dropped_groups` / `peak_original_tokens`），失败的
回合也记——撞上下文超限的那些恰恰是压缩压力最大的样本，只记成功回合会把分布裁掉一头。
它和批级计数共用同一个 `Usage` 类，两个数不会各自漂移。已有的 4,000 条轨迹没有这个字段，
所以对照要等下一批采集。

即便如此，光有观测数据还是定不了因果——压缩与步数在观测里是共变的。要定论仍得跑一组
`--context-window 32768` 的诊断做干预对照，那时按回合的 `compactions` 才能把「压过的
长回合」和「没压过的同样长的回合」直接对上。窗口一改就和 baseline 不同口径，不能混进
主评测。

参考实现 GRPO 的 group size 只有 4，组内优势信号方差过大，是其 RL 增益仅
1.5 个点的一个合理怀疑方向。本项目 SFT 已经把成功率推到 0.61，GRPO 的提升空间和
参考实现（SFT 60.5% → GRPO 62.0%）不在同一个起点上，group size 与 KL 系数都要重调。

GRPO 实测（权重 `outputs/models/grpo`，日志 `outputs/logs/grpo_full.log`）：40 轮 ×
24 题 × G=8 = 7,680 个回合，148 个 optimizer step，**6.56 h**。采样时间随策略变好而
下降（第 0 轮 549 s → 后期约 230 s，`repeat_loop` 从 32 条降到 8 条），所以每轮从
17.6 min 收敛到约 8 min。

训练期 `gold_purchase`（采样温度 1.0，全部 192 条）：前 5 轮均值 108/192 = **56.2%**，
后 5 轮 137.4/192 = **71.6%**。这不是评测数字——采样用 temperature 1.0 且每轮换题，
公平比较要在留出集上用同一批题、同一温度重跑。

**`mean_reward` 这一栏不能当性能指标看**：它只统计进了梯度的组（`stats.rewards`
在丢弃无方差组之后才 extend）。被丢掉的恰恰是「8 条全对」的满分组，于是这个均值
系统性偏低，而且随训练推进越偏越多——它是**给优势尺度用的诊断量**，不是成功率。
看性能要看 `reward_types` 里的计数，那个是全部 192 条的。

这个坑已经修掉了，但**本次运行的 `train_log.jsonl` 仍是旧格式**，读它时上面那段仍然
适用。`GroupStats` 现在不再提供叫 `mean_reward` 的字段——一个读起来像性能指标而实际
不是的名字，光写文档挡不住下一个人误读。改成两个各自说清口径的字段：
`mean_reward_all`（全部有效回报，看性能看这个）与 `mean_reward_kept`（只含进梯度的
轨迹，配合 `groups_no_variance` 读的诊断量）。`tests/test_grpo.py` 里
`test_两个回报口径必须分开` 钉住两者必须不等且旧字段不许复活。

有效样本随训练衰减是这次运行的主要局限：全组同结局而被丢弃的组从 4.6/24 涨到
10.2/24，进梯度的轨迹从 163 掉到 96，后半程每轮实际学习量只有前期六成。这也修正了
下面那段模拟的结论——它既低估了初始死组率（预测 0.01%，实测 12.5%），也没预见到它
会随训练上升。**真实数据更支持 G=16**，或按组内方差动态筛题。

group size 用实测回报分布做了模拟：G=4 有 1.795% 的组全组同结局（整组白跑），
组内极差均值 1.388；G=8 降到 0.010% / 1.688；G=16 是 0.000% / 1.784。收益的拐点在
G=8，再往上只是线性地加采样成本。**取 G=8**。（模拟按边际分布 i.i.d. 抽，忽略了同题
内部的相关性，真实的死组率会比这高；但三档的排序不受影响。）

KL 系数取 **0**，不要 reference model（DAPO 的做法）。省下来的是每卡 ~2.3 GB 显存和
一整次前向（约占单步时间的 40%）——在一个采样已经占七成 wall-clock 的循环里，这次
前向买到的只是一个「别漂太远」的软约束。换成三件更直接的：lr 压到 1e-6、梯度裁剪
1.0、每轮记回报与 reward_type 分布。漂移会先在后者上看见，而不是等 KL 报警。

μ 取 1（一个 batch 只走一次梯度），于是重要性比恒等于 1，clip 是恒等操作——不实现它，
而不是实现一个永远不生效的分支。loss 直接写成极限形式 `Σ A·CE / Σ 1`，等价于带基线的
策略梯度 `−Σ A·log πθ`，还能原样复用 SFT 那段分块 fp32 上采的 CE（`tests/test_grpo.py`
里两条测试分别钉住「加权 CE == −Σ A·logπ」和「分块求和 == 整体求和」）。

权重同步用**重启 vLLM**，不是 RPC 热更新。热更新要对上 vLLM 内部的参数排布再加一个
NCCL 组，而它失败的方式是静默的——服务照常应答，只是用的还是旧权重，训练曲线上看不
出来。重启是幂等的，代价是每轮约 2 分钟。写权重前必须先停服务：从第 2 轮起被覆盖的
正是 vLLM 当前 mmap 着的目录，覆盖同名文件不会报错，只会让推理结果变成垃圾。

`hermes` 在 `serve_model.sh` 已配好，并离线验证过：vLLM 0.25.1 里解析器路径变了
（不再是 `vllm.entrypoints.openai.tool_parsers`），改用 `register_lazy_module`
注册表，`ToolParserManager.get_tool_parser("hermes")` 能取到
`Hermes2ProToolParser`。12 个工具 schema 全部合法，中文 query、asin、空参数三种
情况往返都正确。

driver too old。绕过它去装 cu128 的 torch 是死路——vLLM 算子会静默返回全零，
详见 [environment-notes.md](environment-notes.md) 的「CUDA forward compatibility」。

### 两个半程在做相反的事

探索性地评了 `iter019`（同口径 k=4）。配对差值：SFT → iter019 **+4.76 pp
[+2.78, +6.79]**，iter019 → iter039 **+2.63 pp [+0.89, +4.41]**。后半程边际递减
但**不为零**，区间不跨 0——尽管无方差死组从 4.6/24 涨到 10.2/24、进梯度的轨迹从
163 掉到 96，后 20 轮仍买到了 2.6 个点。

（顺带修正噪声下限的估计：这里 k=4 的实际半宽是 ±1.76 pp，比外推的 ±2.0 略紧。
两个同血缘的检查点在题上的行为相关性更高，配对因此消掉更多方差。分辨率不是模型无关的
常数，比较越相似的模型越紧。）

真正值得记的是**两个半程的行为改变方向完全相反**，且在每个难度桶上都一致：

| 难度桶 | 题数 | 错买率 SFT → i019 → i039 | repeat_loop 占比 SFT → i019 → i039 |
|---|---|---|---|
| 1-2 | 91 | 0.028 → **0.039** → 0.014 | 0.184 → **0.036** → 0.096 |
| 3-4 | 185 | 0.053 → **0.093** → 0.052 | 0.166 → **0.045** → 0.127 |
| 5-7 | 178 | 0.058 → **0.074** → 0.037 | 0.163 → **0.041** → 0.117 |

前 20 轮把 `repeat_loop` 压下去（全体 329 → 80 条）、`max_steps` 从 58 压到 4，
代价是错买率上升（108 → 153 条）：学会了**别再瞎逛，赶紧下手**。后 20 轮把错买率
砍掉一半（153 → 84），代价是 `repeat_loop` 回升到 220：学会了**没把握时宁可继续找
也别买错**。

这正是 reward 的序诱导的：`wrong_purchase` 是 −0.85，`repeat_loop` 是 −0.65。不确定
时继续找严格优于买错，GRPO 找到了这个梯度。所以「后半程有没有白跑」的答案不只是
「+2.6 个点」，而是「它在重新校准冒险与保守的边界」——只看成功率会把这件事看丢。

### 预注册的预测：三条中，一条错

中的三条：增益全部落在条件买对率（走到终局率只动了 0.2pp）；`repeat_loop` 占比
16.45% → 11.00%（终局内口径 16.53% → 11.03%，是真实占比下降而非分母效应）；
`early_abstain` 保持 0，没有用弃买换错买率。

**错的一条是「错买率随难度下降，且高难度桶降得更多」**，而且错在有判别力的那一半。
总错买率确实降了（0.0540 → 0.0420），但 8+ 桶纹丝不动：0.100 → 0.103（区间重叠严重，
诚实的说法是「没改善」而非「变差」）。降的是 1-2 和 5-7。

上面那张表给出了诊断：**i039 在 8+ 桶的 `repeat_loop` 占比只有 0.043，是四个桶里最低的**，
而其他桶都在 0.10-0.13。也就是说在约束最多的任务上，模型既没有更会核验，也没有退回到
「没把握就继续找」——它照买不误。「不确定就别买」这个策略要求模型**知道自己不确定**，
而约束一多，看起来都对的商品变多，它是自信地买错。

结论：GRPO 推动的是**谨慎程度的校准**（在模型能察觉自己没把握的中低难度任务上生效），
不是 roadmap 判定的**约束核验能力**。8+ 桶的错买率绕了一圈回到 SFT 的水平，是这次
运行最清楚的未解决问题。下一轮该冲这里，而不是继续加轮数——后 20 轮的边际已经从
+4.8 掉到 +2.6，同时死组率翻倍。

### +7.41 pp 在 run 间稳不稳：三个 seed 的答案是「稳，但区间要放宽」

R1。动机是已发布的 +7.41 pp [+5.40, +9.51] 那个区间**只覆盖评测采样噪声**——它由同一份
权重的 bootstrap 得出，回答的是「再采一次会怎样」，而不是「换个 seed 重训一次会怎样」。
一个关于训练方法的结论却只报了采样不确定度，缺的那一项恰好是最容易让人过度自信的。

补了 seed 43 / 44（各 6.0–6.3 h，40/40 轮，6 卡，超参与 seed 42 逐项一致、只差 `seed`），
三者对**同一份未重采的 SFT 轨迹**配对。基线不重采是有意的：要量的是 GRPO 一侧的 run 间
散布，重采基线会把 SFT 的采样噪声混进来，而那一项在 [eval-preregistration.md](eval-preregistration.md)
里已经量过。判定规则和判定脚本都写在数字出现之前，见
[multiseed-preregistration.md](multiseed-preregistration.md) 与 `scripts/analyze_multiseed.py`。

| seed | 配对 delta | 采样区间（bootstrap） | 配对题 | 轮数 |
|---|---|---|---|---|
| 42（已发布） | +7.41 pp | [+5.40, +9.51] | 495 | 40 |
| 43 | **+9.75 pp** | [+7.84, +11.72] | 494 | 40 |
| 44 | +7.36 pp | [+5.30, +9.36] | 495 | 40 |

主统计量（预注册定死 n=3、t₂,₀.₉₇₅ = 4.30）：**d̄ = +8.17 pp，s = 1.37 pp，
95% t 区间 = [+4.78, +11.56] pp**，不跨 0 → **结论升级**：GRPO 的提升在 run 间稳定。
按规则停在 3 个 seed。三条次要预测全中（s 落在预测的 1–3 pp；三个 delta 全为正；
`early_abstain` 三个 run 都是 0）。判定输出存档在
`outputs/rollouts/multiseed_verdict.txt`。

三件比「升级」本身更有用的事：

**已发布的 +7.41 在三者里偏低**（7.36 / 7.41 / 9.75），均值 +8.17 比它高 0.76 pp。所以
那个数不是挑出来的好运气，报它反而略偏保守。这一点事前无法知道——正是要补 seed 的理由。

**run 间散布和采样噪声是同一量级。** 采样半宽 ±2.05 pp，run 间的 t 半宽 ±3.39 pp。
换句话说，只报配对 bootstrap 区间会把一个训练方法结论的总不确定度低估掉将近一半。
以后任何「换了个训练配置、涨了 X pp」的说法都要过这道尺子。

### 第 3 个 epoch 值不值：问的是 epoch，起作用的是 LR 计划长度

E2（`scripts/eval_sft_variants.sh`，四份 SFT 权重 × grpo_val 200 题 × k=4，判定规则写在
脚本头部、跑之前）。四份权重：已发布的 `sft`（6 卡 3 epoch）、S4 重训的 `sft_e3`（3 epoch）、
S4 独立的 `sft_e2`（**余弦在 2 个 epoch 内退到 0**）、`sft_e3/epoch2`（`sft_e3` 跑到第 2 个
epoch 末的 checkpoint，**余弦没退到 0**）。

关键设计是最后两份：`sft_e2` 与 `sft_e3/epoch2` 见过**一样多的数据**（都是 2 个 epoch），
差别只在 LR 计划。有了这一对，「多训一轮」和「LR 计划更长」才能分开。

| 比较 | 差值 | 95% 配对区间 |
|---|---|---|
| 朴素「3 epoch vs 2 epoch」（`sft_e3` vs `sft_e2`） | **+7.56 pp** | [+3.97, +11.03] |
| ├ LR 计划长度（`sft_e3/epoch2` vs `sft_e2`） | **+6.71 pp** | [+3.68, +10.00] |
| └ 第 3 个 epoch 本身（`sft_e3` vs `sft_e3/epoch2`） | **+0.85 pp** | [−2.56, +4.15] |

两项相加正好是 7.56。**朴素比较记在「多训一轮」账上的几乎全是 LR 计划长度。** 机制不神秘：
`sft_e2` 的余弦半周期压到 2 个 epoch，于是在同样这两轮数据上处处用更低的 lr，总 LR 积分
更小、学得更少。它不是「训得刚好」，是欠训。

推论一条，可以直接用：**要省时间就用 3-epoch 的余弦计划、只跑 2 个 epoch**——就是
`sft_e3/epoch2` 这份权重本身。省三分之一 wall-clock，代价 +0.85 pp 测不出。而**不能**把
`epochs` 直接设成 2，那会连带压短计划。这两种「2 epoch」在 val loss 上几乎分不开，只有
在任务成功率上才拉开 6.71 pp——又一处 val loss 会骗人的地方。

`scripts/run_rollout.py` 里搜不到 `finish_reason`，轨迹文件里也没有这个字段。也就是说
**撞了 `max_tokens` 被截断的回复，和「模型想了想决定什么都不做」在记录里完全同形**，都
落成 `no_tool_call`。这个洞不是 v2 引入的，它一直在，只是 v1 的截断率低到没暴露。

修法很小、优先级却高：把 `finish_reason` 存进轨迹，`length` 单独算一类状态。不做的话，
以后每一次「终局率掉了」都得重走一遍这次的 grep 考古才能知道是策略问题还是预算问题。

#### 原先写在这里的判据错在哪

这一节原来的标题是「退化是众数移了，**不是**格式漂移」，靠下面两条温度与难度证据否掉了
格式漂移。**否错了**，但错的是标签而不是证据：当时把「格式漂移」默认理解成「输出随机
坏掉」，而真实情况是**众数移到了另一个确定的格式**。两件事同时成立——确实是众数移了，
移过去的那个众数就是基座 Qwen2.5 的 Hermes 工具调用格式。

所以下面这两条证据一个字都不用改，它们现在**支持**而不是反对格式漂移：

- **降温让病更重。** 同一份 iter039 权重：训练日志里温度 1.0 的 `no_terminal` 是
  9/192 = **4.7%**，而评测温度 0.7 是 **13.85%**（(272+5)/2000）。格式坏掉的输出住在
  分布的尾巴上，**降温应该让它变少**。降温反而重 2.9 倍，只能说明「不发工具调用」已经
  在那些状态下靠近**众数**——是策略众数真的移了。
- **它随难度单调加重，且难题上回合最短。** `grpo_v2` 按约束数分层：

  | 难度桶 | 轨迹 | 成功率 | `no_tool_call` 占比 | 平均步数 | 错买率（终局内） |
  |---|---|---|---|---|---|
  | 1-2 | 364 | 0.6938 | 11.0% | 6.71 | 0.0370 |
  | 3-4 | 740 | 0.6174 | 10.5% | 7.66 | 0.0605 |
  | 5-7 | 712 | 0.6208 | 14.6% | 7.21 | 0.0497 |
  | 8+ | 184 | 0.5109 | **27.2%** | **5.94** | 0.0821 |

  最难的一桶里超过四分之一的回合模型根本不动手，而且**恰恰在这一桶回合最短**——不是
  耗尽步数才失败，是在第一个难判断点上就死。（原来这里写「格式漂移应当与难度无关，所以
  这条否掉格式漂移」。这个推理作废：它假定的是随机性的格式损坏，而实际是条件性的格式
  切换，完全可以与难度相关。）

  **难度梯度有一个候选解释，但 14:35 把它降回假设：token 预算。** 形式是：`max_tokens`
  默认 1024，题越难则调用前的推理正文越长，留给调用的预算越少，顶到上限被截断的概率越高；
  截断造出不完整的末块，于是整条回复回落成纯 content。

  它的吸引力在于**一次解释本表里两列**：`no_tool_call` 占比随难度单调升（11.0 → 27.2%），
  而平均步数在最难那桶反而**最低**（5.94，全场最低）——不是探索到没步数才失败，是头几步
  就被打死。原来那个纯「散文长度」的假设只能解释第一列。

  **但它是假设，不是结论。** 支持它的是 83 条截断硬签名加上「复读块必须很短」这条从 1024
  反推出来的约束；缺的一环是**那 83 条从没按难度分层过**——梯度本身还没被直接验证。
  （14:05 我把它写成「不再是猜的」，那是过头了；14:35 又以为算术不成立而整条否掉，那是
  另一个方向的过头。）

  要测的：(a) 存 `finish_reason`（见下节），直接看被截断回复占比是否随难度单调升；
  (b) 把调用前正文 token 数与是否截断做相关。两条都要等 #21。

于是 `training/grpo.py:23` 那句注释失效了：「这一档在 SFT 权重上只占 ~0.5% 的回合，
取值不敏感」——在 13.6%、且难题上 27% 的时候，它既不是 0.5% 也不再不敏感。

**尚未拆开的混淆：** 4.7% 出自训练池采的 24 题，13.85% 出自 500 题评测池，两池难度构成
不同，而上表说明难度本身就能造出 2.5 倍差别。所以温度与池子现在缠在一起。
`scripts/eval_grpo_v2_snapshots.sh` 里的 `iter039_t10` 臂就是来拆它的：同池、同权重，
只把温度换成 1.0。同一个脚本顺带扫 iter004…039 定位塌陷是哪一轮开始的。

**这个扫描的主指标要换成标签率**（content 含字面量 `<tool_call>` 的比例），不是成功率也
不是终局率：成功率在 n=200 下分辨不出相邻快照，而终局率只是标签率经过解析器之后的下游
后果，中间隔了一层「首块合法但被尾部垃圾带走」的损耗。标签率是这条因果链的源头，一条
grep 就能从存下来的轨迹里算，不额外花 GPU。

**而标签率还要拆成两列报**（脚本里已经加好：`少量` = 1-2 块，`复读` = ≥30 块）。因为双峰
的两侧修法不同，总量的升降会把它们混掉。由此多出一条**预注册判读 B**：复读退化是**低温**
的已知病（贪心重复），高温反而打断它——所以若那 38% 的复读峰是温度造的，`iter039_t10`
（温度 1.0）应当是**复读列塌得比少量列多**，而不只是总标签率下降。若复读列基本不降，那
就是策略本身学会了复读，得回到 iter 曲线定位它是哪一轮长出来的。

顺带说，「低温更容易复读」这一点让本节前面那条**降温反而更严重**的证据有了比「众数移到
Hermes 格式」更省的解释：不需要假定众数整体搬家，只需要低温更容易掉进复读、复读撞满 1024
token、截断必然毁掉末块。两个版本都与已有数据相容，判读 B 就是用来分它们的。

#### 一个曾经写进本节、被跨代对比否掉的机制

先前这里写的机制是：优势为 `r − group_mean` 且不除 std，**整组同归于败时优势恒为 0**，
零方差组还会被整组丢掉 → 难题不产生梯度 → 漂移无人纠正；并把 `groups_no_variance`
从 4/24 涨到 11-13/24 当作佐证。**把 v1 的训练日志逐轮拉出来对比之后，这条作为「两代
之差的原因」被否掉了。**

两份日志是逐轮可比的：同一个训练题池、同一个采样顺序，所以同一 iteration 抽到同一批题。
证据是 `gold_purchase` 在中段几乎重合，连第 18 轮那个掉到 97/98 的坑都在同一位置
（v1 140/97/134/137 vs v2 142/98/142/131，iter17-20）。在此前提下：

| 末 4 轮（iter36-39） | `grpo`（v1，+7.41 pp） | `grpo_v2`（−6.29 pp） | 判定 |
|---|---|---|---|
| `groups_no_variance` | 8 / 13 / 11 / 12 | 5 / 12 / 13 / 11 | 分不开 |
| `kept` 轨迹数 | 128 / 80 / 98 / 96 | 151 / 88 / 82 / 104 | 分不开 |
| `gold_purchase` 均值 | 137.25 | 133.75 | 差 1.8 pp，噪声内 |
| 每回合 completion token | ~465 | ~449 | 差 3.5% |
| **`no_terminal` 合计** | **6 / 768** | **20 / 768** | **3.3 倍** |

`groups_no_variance` 在 v1 是 3/24 → 12/24，`kept` 是 163 → 96——**塌陷幅度与 v2 相同，
末期保留的轨迹甚至比 v2 更少，而它涨了 7.41 pp。** 所以组内方差塌陷是**这个配方的固有
行为**，不是 v2 特有的病，「恢复难题的组内方差」得不到证据支持，不应作为下一个 run 的
主要改动。

机制的算术本身仍然成立（全组失败确实优势为 0，均值中心化确实抹掉全组共有的常数偏移，
所以 `invalid_reward = −1.0` 确实使不上劲），只是它同样适用于 v1，因此解释不了差异。
上面那一节（「众数移到了基座的工具调用格式」）的结论不依赖这条机制——它现在建立在直接
读出的 `<tool_call>` 标签统计上，比温度与难度两条间接证据强得多，更不受影响。

**但均值中心化这条算术在新机制下重新变得相关，只是位置换了。**它解释不了 v1/v2 的差异，
却解释了**为什么格式漂移一旦发生就不会被自己纠正**：漂掉的回合拿 `invalid_reward = −1.0`，
而整组一起漂掉时优势恒为 0，于是这个惩罚使不上劲。v1 之所以没事，不是因为它有纠正机制，
而是因为它没漂到那个程度（5/2000）。所以下一个 run 要的不是「更狠的 invalid_reward」，
而是一个**不依赖组内对比**的格式约束：非零 KL 锚，或在 token 级直接惩罚正文里的
`<tool_call>`。

（另有一个曾以为找到的判别量也被否掉：`render_stats.tokens.p90` 出现中段 v1 15520 <
v2 16941、末段 v1 19330 > v2 15314 的交叉，看着像「v1 学会在难题上多花 token，v2 学会
少花」。但 `render_stats` 统计的是**过滤后的** `kept`，而被滤掉的正是零优势组——最易与
最难的题，两代组成不同故不可比。换成未过滤的 `rollout_usage.completion_tokens` 逐轮
差分：中段每回合 v1 101486/192 与 v2 101630/192 完全一致，末段 89379 vs 86208，只差
3.5%。那个 21% 的差距基本是过滤组成造成的假象。）

#### 最要紧的一条：训练 reward 看不见这个退化

上表真正的含义不是「哪个量能分开两代」，而是**几乎没有量能分开**。一个端到端掉 6.29 pp
的 run，在自己的优化目标上和一个涨 7.41 pp 的 run 长得一样：`gold_purchase` 曲线重合、
`mean_reward_all` 照常从 0.21 涨到 0.59、方差塌陷同步、token 花费一致。

唯一携带信号的是 `no_terminal`，而它被温度差压缩了约 **17 倍**：评测口径是 13.85% vs
0.25%（**55 倍**），训练口径只剩 2.60% vs 0.78%（**3.3 倍**）。而且单看一轮完全没用
（1-9 / 192 是噪声量级），必须把末 5 轮池化**并且拿 v1 当参照**才勉强显著
（20 vs 6，泊松下 p≈0.01）——也就是说，只跑 v2 这一个 run 的话，训练日志里没有任何
可行动的信号。

设计时写的「漂移会先在 `reward_type` 分布上看见」确实发生了，但幅度被温度压到了看不出来
的水平。**监控口径必须和判定口径一致，否则等于没监控。**

##### 直接量了病根本身，结论比上面更狠：不是不灵敏，是反向

`outputs/models/{grpo,grpo_v2}/rollouts/` 存了全部 40 轮训练 rollout（192 条/轮），所以
病根指标——content 里含字面量 `<tool_call>` 的比例——不用花 GPU 就能逐轮量出来：

    v2 每轮标签数，十轮一段：  11  10   7  13    → 41/7680 = 0.53%
    v1 同口径：                20  10  12  18    → 60/7680 = 0.78%

v2 的曲线**是平的**，全程看不出上升趋势（只有 iter039 的 6 条真离群，Poisson(1.03) 下
P(X≥6) ≈ 0.0005；30-39 段 13 对 20-29 段 7 检验不出来）。而 **v1 训练期的标签率比 v2 还
高**，v1 最后一轮是 0、v2 最后一轮是 6。

| | 训练（温度 1.0，训练池） | 评测（温度 0.7，评测池） | 方向 |
|---|---|---|---|
| grpo v1 | 0.78% | 0.25% | ÷3.1 |
| grpo v2 | 0.53% | **12.8%** | **×24** |

所以单看训练 rollout，v2 在这个指标上比 v1 **更干净**——而它正是最后让 v2 输掉 6.29 pp 的
指标。监控不是不灵敏，是在总量上**反着走**。

这张表还顺手把温度/池子的混淆压掉了大半：两个 run 经历同一个池子变化和同一个温度变化，
所以「池子更难」或「温度更低」作为**主效应**必须对两者同样起作用，可它对 v1 是 ÷3.1、
对 v2 是 ×24，差 75 倍。剩下没排除的只有**交互项**（v2 特有的难度敏感性 × 评测池更难），
这正是 `iter039_t10` 要切的。**预注册预测**：温度是放大器 → t10 掉到 3% 附近；池子是
放大器 → t10 仍是十几个点，那么训练期那 0.53% 从一开始就没有可比性。

**结果（08-14 21:48）：两个分支都错了，而第三种解释比它们都硬。** 详见下面「快照曲线」
一节——简短版是 t10 的标签率 **0.1537 比 t=0.7 的 0.1325 还高**（温度方向反了），但池子
难度也不成立，因为两个**互不相交**的留出池给出几乎相同的终局率（grpo_val 0.8588 vs
500 题池 0.8615）。真正区分的是**训练池 vs 留出池**，不是这两个候选变量中的任何一个。

##### 于是 in-loop val 的规格是什么

这给「把 grpo_val 接进主循环」换了一个比 E1 硬得多的动机。E1 收尾时的说法是「iter034 与
iter039 分不出，所以选点价值有限」，口径偏软。D2 给出的理由是结构性的：**训练日志无法
替代评测温度下的验证**，所以 in-loop val 的价值不在「挑一个更好的 iterate」，而在
**「在 6.5 小时烧完之前发现整个 run 的方向错了」**。

而且现在能写出具体规格，不只是「接进去」：

1. **用极值/是否发生，不要用发生率的均值。这一条排第一，且不花任何钱。** 把「一条回复里
   出现 ≥3 个标签块」这个判据拿去扫已经免费存着的 40 轮训练 rollout（温度 1.0，192 条/轮，
   共 7680 条），**只有 iter039 命中**；阈值放到 5 块、30 块，答案一样。iter039 里 3 条
   是 ≥30 块的连续复读。也就是说信号在训练温度下**本来就可见**，只是被「标签率」这个均值
   统计量抹平了（全程 0.53%，趋势平坦）。零膨胀、高度集中的现象要用「首次出现」去抓，
   不能用发生率。

   **这个判据的背景噪声是 0/6000**：`sft`、`grpo`(v1)、`sft_v2` 三个模型各 2000 条评测
   轨迹里 ≥3 块的一条都没有，而 grpo_v2 是 134/2000。所以它不需要挑阈值、比基线、算显著
   性——背景率是零，**命中一条就该停下来看**。这正是它比标签率好用的地方：标签率在 sft_v2
   上有 0.35% 的底噪，要把 0.53% 和 0.78% 分开得攒样本量；而这个判据第一次命中就是报警。
2. **必须在留出池上采，温度无关紧要。**（08-15 改口，原文是「必须用评测温度 0.7，不能用
   训练温度 1.0」。）原来的依据是「1.0 下 0.53%、0.7 下 12.8%」，但那两个数**同时换了池**
   ——0.53% 出自训练池、12.8% 出自留出池。把池固定住再看温度，方向是反的：留出池上
   t=1.0 是 **15.37%**，比 t=0.7 的 13.25% 还高。所以温度不是放大器，**池才是**：

   |  | 训练池 | 留出池（grpo_val） | 留出池（500 题） |
   |---|---|---|---|
   | t=1.0 | 0.53% | 15.37% | — |
   | t=0.7 | 4.7% | 13.25% | 13.85% |

   两个**互不相交**的留出池给出几乎相同的终局率（0.8588 vs 0.8615，差 0.27 pp），所以
   也不是「题目难度」。剩下唯一的变量是**这批题在训练里见过没有**——这是记忆化的签名，
   而它的直接后果是：**训练 rollout 的监控在结构上看不见这个病，grpo_val 能。** 这条因此
   不是「让信号更强」，它是 in-loop val 存在的理由本身。按训练温度 1.0 采反而更省事——
   在留出池上它照样看得见，甚至更明显，于是不必为了监控另起一套采样参数。
3. **主指标用标签率（拆成少量/复读两列），不用成功率。** 它是因果链源头，一条 grep 就能
   算，且不受 n=200 时成功率分辨不出相邻快照的限制。
4. **单轮的发生率不够，按 5 轮池化**——但这只针对第 3 条的率值；第 1 条的「是否发生」判据
   单轮就有效，这正是它更值钱的原因。
