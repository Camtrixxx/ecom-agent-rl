### 卡的分配（与计划的偏差，必须记进结论）

计划里 S4 假定 7 张卡。实际 E1 评测占着 GPU 1-2（它在两张卡上交替预热下一个模型），
所以 **S4 用 GPU 3-7 五张**。串行等 E1 跑完再用 7 卡要 6.1 h，并行只要
max(3.8 h, ~3.3 h)。代价是步数变了：

| 卡数 | per_rank = 648/卡 | steps/epoch = per_rank//4 | 3 epoch 共 |
|---|---|---|---|
| 6（已发布的 SFT） | 108 | 27 | 81 |
| 7 | 92 | 23 | 69 |
| **5（本次 S4）** | **129** | **32** | **96** |

S4 内部的三处比较（e3 / e2 / e3-epoch2）共用同一个 world_size，自身自洽；且 S1 修好
之后 val loss 已经与卡数无关。但 **S4 的 val loss 与已发布 SFT 的 0.39249 不可直接比**
——后者是在丢掉 3 条最长验证样本的口径下量的（见下）。

**更要紧的一条：`sft` vs `sft_e3` 这一对不能当作「重训的 run 间方差」来读。** 卡数变了
就等于 optimizer 的 global batch 变了——`grad_accum 4 × 5 卡 = 20 批`，而已发布的 SFT
是 `4 × 6 = 24 批`。所以那一对同时混了「重训」和「批大小」两件事，只能当参考锚。
S4 真正要回答的「第 3 个 epoch 值不值」完全落在 5 卡这一族内部，不受影响。

**推论：R1 的两个 seed 必须用和已发布 seed 42 相同的 6 张训练卡**
（`GPU_VLLM=1, GPUS=2,3,4,5,6,7`，即 `train_grpo.sh` 的默认值）。同样的道理：4 卡的
global batch 是 8 批而 6 卡是 12 批，若 seed 43 用 4 卡、seed 44 用 6 卡，卡数就和 seed
混在一起，恰好毁掉这个实验要量的 run 间方差。因此 R1 只能等 E2 让出 GPU 1-2，不能为了
填满空闲卡而改卡数。

### S1/S2/S3：train_sft.py 三处修复

**S1（错）** `evaluate()` 之前用 `shard()` 切验证集。`shard()` 为了对齐 FSDP 的集合
通信把各 rank 截到等长，丢掉尾部 `len(batches) % world_size` 批。训练侧丢一点无所谓
（每个 epoch 重新 shuffle，长期每条都会被采到），验证侧是致命的：
`token_budget_batches` 先按长度排序且 val 从不 shuffle，所以每个 epoch 丢的**永远是
同样那几条最长的样本**，而丢几条**取决于卡数**——6 卡丢 3 条、7 卡丢 6 条、8 卡丢 7 条。
已发布的 0.39249 实际是 295 条样本上的数，且换卡数就变。

修法：新增模块级 `val_rounds()`，按 `batches[rank::world_size]` 分，短的 rank 用
**零权重**重复自己的第一批补齐轮数。轮数对所有 rank 相同（不然 FSDP 卡死在 all-gather），
每条样本恰好计一次权重 1.0。

**S2（缺）** val loss 只进内存 `history`，中途崩了就全丢；且没有 epoch 0 的基线点，
「第 3 个 epoch 只降 0.0032」这类判断没有起点可依。修法：`emit()` 每条记录即时追加到
`train_log.jsonl`；训练前先量一次记为 epoch 0；`metadata.json` 里把含糊的 `final`
拆成 `final_train` + `val_curve`。

**S3（错）** `steps_per_epoch` 用 `math.ceil`，而训练循环是
`range(0, per_rank - grad_accum + 1, grad_accum)`，只走完整的 grad_accum 组，实际步数
恒为 `per_rank // grad_accum`。ceil 会让 `total_steps` 超过所有 epoch 加起来能走的步数，
于是 while 多跑一个残 epoch 去补，余弦在残 epoch 中途才退到 0，`--save-each-epoch`
还会多写一个目录。之前没暴露纯属整除的巧合：6 卡 per_rank=108、7 卡 92 都被 4 整除；
8 卡 per_rank=81 就会踩（ceil 21 vs floor 20 → total 63 而 3 个 epoch 只有 60 步）。
顺带补了 `steps_per_epoch == 0` 的守卫——那种情况下 while 只看 `step < total_steps`，
会永远转下去。

三处各配了回归测试，`tests/test_train_sft.py` 26 条，全套 389 passed / 3 skipped。为了让
逻辑可测，`val_rounds` / `steps_in_epoch` 从 `main()` 的闭包里提到模块级。

**冒烟**（5 卡，`--limit 48 --max-train-steps 2`）：epoch 0 量到 val 1.024，1 步后 0.798，
末步 lr 退到 0，`metadata.json` 里 `val_curve` 两点齐全、`final` 已消失。

先在 2 卡上试过一次，rank0 在 epoch-0 验证之后退出 1，当时 GPU 4 已到 79.9/80 GB。
最可能是 2 卡下 FSDP 只把优化器状态切成两份（约 40 GB/卡，6 卡时约 13 GB）导致的 OOM，
**但当时用了 `| tail -30`，原始异常被截掉了，这个归因是推断而非实证。** 换到 5 卡即通过，
而 5 卡正是 S4 要用的配置，所以没有继续追这条。

顺带核了两件与改动相邻的事：`evaluate()` 结束时会 `model.train()` 回去
（`train_sft.py:376`），且 Qwen2.5 的 `attention_dropout=0.0`，所以我新加的「训练前先量
一次」不会改变 epoch 1 的训练行为；`save()` 只 gather 一份副本转 bf16 写盘、两端各一道
barrier，中途存不动活模型。`--save-each-epoch` 的 `if ... and not stop` 保证最后一个
epoch 不重复存——而这一条恰好依赖 S3 的 floor 口径，ceil 时会多进一个残 epoch、多写一个
`epoch3/`。

### 「第 3 个 epoch 只降 0.0032」的出处，以及它错在哪

那个数来自已发布 run 的控制台日志 `outputs/logs/sft_full.log`：

```
[15:06:59] epoch 1 验证 loss 0.44066
[15:40:33] epoch 2 验证 loss 0.39567
[16:14:13] epoch 3 验证 loss 0.39249
```

0.39567 − 0.39249 = 0.00318。**但这三个数都是在 S1 的 bug 下量的**（日志打印「验证样本
298」，实际只算了 295 条——`shard()` 把 6 卡截到等长，丢掉 3 条最长的）。

为了把 S1 的影响单独摘出来，拿**已发布的那份权重**用修好的代码在完整 298 条上重测了一次
（GPU2 空着，单卡一次前向，复用 S2 新加的「训练前先量一次」，没写新代码）：

| 口径 | val_loss |
|---|---|
| 已发布：`shard()`，295 条 | 0.39249 |
| 修复后：`val_rounds()`，298 条 | **0.39379** |
| **S1 造成的偏乐观** | **+0.00130** |

方向与机制一致：丢掉的是最长、loss 最高的样本，丢了报出来的就偏低。

**值得停下来看一眼的对照：S1 这个测量误差（0.0013）是「第 3 个 epoch 真实收益」
（0.0003）的 4 倍。** 也就是说，原本用来判断「第 3 个 epoch 值不值」的那个 0.0032，
是在一把量不准的尺子上读的，而尺子的误差比要测的东西还大。

顺带把两个 run 的绝对值也校平了。同在 298 条口径下：已发布 sft 0.39379 vs S4 sft_e3
0.38993，S4 低 0.00386。这**不能**归给「重训的 run 间方差」——5 卡走 96 步、6 卡只走
81 步，optimizer step 数不同（见上文卡数那节）。两个 run 的数据完全一致
（1776 训练 / 298 验证，sha256 相同），差的就是步数。

（第一次跑探针漏传了 `--validation`，白跑一次只写到 `/tmp`，没碰任何产物；不能用
`--limit` 抄近路，它会连验证集一起截断。）

| iter039 vs iter019 | +1.70 pp | [-0.35, +3.92] | 否 |

k=8 下各自成功率：iter019 65.69%、iter034 69.27%、iter039 67.72%（k=4 时分别是
65.56 / 68.81 / 67.91，移动都在噪声内）。

**跑之前写在 `topup_k8.sh` 头部的两条预测都中了**：iter034 vs iter039 的 0.60 pp 差
「大概率仍判并列」——确实不显著；iter019 vs iter034 的 2.64 pp「可能分得出」——确实分出来了。

### E1 的结论

1. **没有提前见顶。** iter034 显著优于 iter019（+2.91 pp，区间不跨 0）。这正是 E1 设计时
   说这套配置「能回答」的问题，答案是训练在 iter019 之后还在涨，不是早就到顶后面白跑。
2. **iter034 与 iter039 分不出。** 没有证据支持把已发布的 iter039 换成别的检查点。
   原始担心的「iter039 是最后一个而不是最好的一个」，在这个分辨率下测不出来——
   而按预注册，测不出来就是结论，不加采样、不挑。
3. 附带：平均 env_steps 从 sft 的 14.63 单调降到 iter014 的 9.78。GRPO 同时在提高成功率
   和降低步数。

配对区间半宽约 ±1.9 pp，比 vs-sft 那一列的 ±4 pp 窄一半多——同血缘模型在同一批题上高度
相关，配对差值的方差小。这正是当初决定「只补三个模型、不补 sft 基线」的依据：补基线是为了
窄化 vs-sft 那一列，而并列要解决的问题根本不在那一列上。

**给训练循环接 in-loop val 的建议因此要改口径。** 原计划的动机是「iter039 可能不是最好的，
需要在训练中选」。E1 的结果不支持这个动机：末尾几个检查点彼此测不出差异，选不选都一样。
in-loop val 真正的价值退化为「早停省算力」——iter019 之后还在涨，所以连早停也省不了多少。
这条建议的优先级应当下调，除非未来的 run 表现出明显的过训退化。

## 2026-08-13 06:52 — S4 结束，「2 vs 3 epoch」的对照被之前搞错了

`sft_e2`（2 epoch，5 卡 64 步）跑完，exit=0，lr 末步 0.0。

| 模型 | 口径 | val_loss |
|---|---|---|
| `sft_e2` | 2 epoch，余弦在 64 步内退到 0 | **0.40310** |
| `sft_e3` @ epoch 2 | 同样看过 2 遍数据，余弦只走到 2/3（lr≈2.5e-6） | 0.39023 |
| `sft_e3` @ epoch 3 | 3 epoch 退火完 | 0.38993 |

健全性检查：两个 run 在 epoch 1 的 val 几乎相同（0.42637 vs 0.42674）——同 seed、同数据、
同卡数，只有 LR 计划不同，符合预期。

**之前的对照搞错了对象。** 「第 3 个 epoch 只降 0.0032」（修正口径后是 0.0003）比的是
**同一条余弦曲线的中点和终点**。但「该训 2 轮还是 3 轮」问的是两个**各自退火完整**的 run
谁更好——那是 0.40310 vs 0.38993，**差 0.0131，比原先那个数大 40 倍**。

也就是说，到目前为止在 val loss 上，**第 3 个 epoch 是值的**，与最初的猜测相反。
这正是 S4 设计成「独立的 2-epoch run」+「3-epoch run 的中点」两份权重的原因；只跑其中
一份都会得出错的结论。

反直觉的一点：退火完的 2-epoch（0.40310）反而比没退火的中点（0.39023）差 0.013。
合理解释是 64 步下模型还欠拟合，提早把 LR 退到 0 等于锁在一个更差的点上——总 LR 积分
更大的那个走得更远。注意这也意味着 `eval_sft_variants.sh` 头部说的「sft_e3/epoch2 vs
sft_e2 的差就是退火的贡献」需要修正措辞：两者的差**不只是**退火，还有「同样步数下累积
LR 不同」这一项，二者在这个设计里分不开。

**但判定仍以任务成功率为准，不以 val loss 为准**——这条写在 E2 脚本头部，理由是
val loss 低不等于成功率高，而报告里报的是成功率。0.0131 的 val loss 差能不能在 ±3.2 pp
的分辨率下看见，是 E2 要回答的。

## 2026-08-13 08:06 — E2 出结论：问题问错了，真正起作用的不是 epoch 数

四份 SFT 权重，各 200 题 × k=4 = 800 回合。以已发布的 `sft` 为基线：

| 模型 | 成功率 | 95% CI | vs sft | 配对区间 |
|---|---|---|---|---|
| sft（已发布，6 卡 81 步） | 58.50% | [53.05, 63.83] | （基线） | |
| sft_e2（5 卡 64 步，退火完） | 54.00% | [48.19, 59.72] | **−4.23** | [−7.78, −0.42] |
| sft_e3_ep2（5 卡 64 步，余弦未走完） | 61.22% | [55.23, 66.84] | +2.44 | [−0.77, +5.64] |
| sft_e3（5 卡 96 步，退火完） | 62.07% | [56.25, 67.47] | +3.29 | [−0.04, +6.37] |

按预注册的并列规则（前两名差 > 3 pp 才补 k=8）：sft_e3 与 sft_e3_ep2 差 0.85 pp，
**判为并列，不补采**。不报排名。

卫生：四份都 0 基础设施失败，非 done 的只有 `rejection_limit`（1~5 条）和 `no_tool_call`
（0~3 条），这两个本来就该算失败。没有 `empty_response`。

### 但上表的基线选错了对象

`sft` 是 6 卡，其余三份是 5 卡。「vs sft」那一列同时混着 epoch 数、退火、和卡数
（global batch 24 批 vs 20 批）三件事。真正干净的比较全在 5 卡族内部——同 seed、同数据、
同卡数。这三份两两配对（正数 = 前者更好，配对题数均 195）：

| 配对 | Δ | 95% CI | 显著 | 这一对唯一变动的是 |
|---|---|---|---|---|
| sft_e3_ep2 vs sft_e2 | **+6.71 pp** | [+3.68, +10.00] | **是** | **只有余弦长度** |
| sft_e3 vs sft_e3_ep2 | +0.85 pp | [−2.56, +4.15] | 否 | 多走的第 3 个 epoch |
| sft_e3 vs sft_e2 | +7.56 pp | [+3.97, +11.03] | 是 | 上面两项之和 |

**第一行是整晚控制得最干净的一次比较。** `sft_e3_ep2` 和 `sft_e2` 都是 64 个 optimizer
step、同一份数据、同一个 seed、同样 5 卡，连数据顺序都一样；唯一的差别是余弦按 96 步
铺还是按 64 步铺——即 step 64 时 LR 是 2.5e-6 还是 0。差 6.71 pp，区间不跨 0。

第二行说：多走的那 32 步（整个第 3 个 epoch）买到的东西**测不出来**。

### 结论：「第 3 个 epoch 值不值」这个问法本身有问题

7.56 pp 的总差里，6.71 pp 归给 LR 计划，剩下 0.85 pp 归给多走的一个 epoch 而且测不出。
也就是说——

- **不是「3 个 epoch 比 2 个好」，而是「别在模型还欠拟合时就把 LR 退到 0」。**
- 想省三分之一算力是可行的：按 3 epoch 的长度设余弦、只训 2 epoch 就停
  （这正是 `sft_e3_ep2` 的口径，61.54% vs `sft_e3` 的 62.39%，并列）。省下 32 步，
  代价在当前分辨率下测不出来。

这和 06:52 记的 val loss 排序完全一致（0.40310 / 0.39023 / 0.38993），两套互相独立的
测量给出同一个次序。E2 头部问的「0.0131 的 val loss 差能不能在 ±3.2 pp 下看见」——
能，而且很清楚。

### 三条限制，别把上面的话说过头

1. **并列不等于相等。** `sft_e3 vs sft_e3_ep2` 的区间是 [−2.56, +4.15]，一个真实存在的
   3 pp 差异完全能藏在里面。结论只是「在 n=200、k=4 这个分辨率下测不出」。
2. **单 seed。** SFT 的 run 间方差从没量过（R1 量的是 GRPO 的）。`sft_e2` 和
   `sft_e3_ep2` 不是同一条轨迹的分叉，从第 1 步起 LR 就不同，所以「LR 计划的效应」和
   「这两个 run 恰好差了这么多」分不开。支持前者的旁证是 val loss 独立给出同向结果。
3. **`sft_e3` vs 已发布 `sft` 的 +3.29 pp 区间是 [−0.04, +6.37]，只差一点点没跨 0，
   且混着卡数。** 不能当结论，但值得记成一个待查问题：已发布的 SFT 基线有可能比同配方
   多走步数能达到的水平低约 3 pp。若属实，GRPO 那个 +7.41 pp 就是踩着一个偏弱的基线量的。
   要证伪只能用 6 卡重训一次 3-epoch SFT，本轮不做。

### 证据二：随难度单调加重，而且难题上回合最短

`grpo_v2.report.json` 的 `stratified.difficulty`（这四个数我原来在总结里记成了

|---|---|---|---|---|---|

| 3-4 | 740 | 0.6174 | 78 | 10.5% | 7.66 |
| 5-7 | 712 | 0.6208 | 104 | 14.6% | 7.21 |

最难那一桶超过四分之一的回合根本不动手，**而且恰恰是这一桶回合最短**。无锚的格式漂移

顺带这也排掉了上一条新提的「上下文压缩后遗症」：压缩压力随步数增长，而出问题最多的

### 机制：均值中心化把地板分的力量消掉了，难题因此没有梯度

优势是 `r − group_mean` 且不除 std，所以**整组同归于败时优势恒为 0**，
`groups_no_variance` 的组还会被整组丢掉。难题上组内经常一致失败 → 那些题**根本不产生
梯度** → 策略在难题上怎么变都没有力量纠正。真正生效的梯度来自简单/混合组，那里学到的
「果断下手」不保证在难题上还成立。

这解释了 `invalid_reward = −1.0` 为什么没拦住：**均值中心化会消掉整组共有的常数偏移**，
地板分只在混合组里有力量。`grpo.py:23` 那句「这一档只占 ~0.5% 的回合，取值不敏感」
在 13.6%（难题 27%）下已经失效——更要紧的是，就算把它调到 −10，全组一致放弃时优势
照样是 0。**这不是取值问题，是它落在了被中心化消掉的那个方向上。**
`groups_no_variance` 从 iter000 的 4/24 涨到 iter035-039 的 11-13/24，与此一致。

所以「加 KL」很可能治错地方。该修的是难题上的零优势塌陷：让难题组里有方差（过采样难题、
或给「走到终局」本身一点分以制造组内差异），而不是给整个策略加一根拴回 SFT 的绳。

### 还没拆开的混淆，以及为此加的一条臂

4.7% 出自**训练池**的 24 题，13.85% 出自 500 题**评测池**，两池难度构成不同——而上表
说明难度本身就能造出 2.5 倍差别。**温度和池子现在缠在一起，光凭已有数据分不开。**

所以给 `scripts/eval_grpo_v2_snapshots.sh` 加了一条判定臂 `iter039_t10`：同池、同权重，
只把温度换成 1.0。t=1.0 掉回 5% 附近 → 温度是放大器；仍是十几个点 → 是池子差异，
训练日志那 4.7% 本来就没有可比性。两种结果都改变下一个 run 怎么配。

### 一条独立于结论的教训：监控口径必须等于判定口径

训练期唯一的漂移监控就是 `reward_type` 分布，而它只在温度 1.0 下采样，对这个退化
**结构性地低报约 3 倍**。iter000 是 5/192、iter039 是 9/192——在 n=192 上完全像噪声，
当时就算有人盯着也不会报警。设计时写的「漂移会先在 reward_type 分布上看见」**确实发生
了**，但幅度被温度压到看不出来。**在温度 1.0 下监控、在温度 0.7 下判定，等于没监控。**

（分类脚本仍然值得跑，它能告诉我那 272 条的正文长什么样、是不是语义完整的「我先不买」。
但它已经不再是拦路的那一步：配下一个 run 需要的判断上面这两条证据已经给了。）

## 14:10 — 把 v1/v2 的训练日志逐轮对齐：我 13:20 提的机制被自己的数据否掉了

等 Bash 的时候做了任务 #15（跨代训练轨迹对比）。这件事只需要读文件，本来排在很后面，

两份日志逐轮可比，这点先要立住：v1 和 v2 用同一个训练题池、同一个采样顺序，所以同一
个 iteration 抽到的是同一批题。证据是 `gold_purchase` 在中段几乎重合，连第 18 轮那个

同一个坑同一个深度。所以下面的逐轮比较不是在比两条无关的曲线。

### 被否掉的：「组内方差塌陷导致难题没梯度」

13:20 我写的机制是：`r − group_mean` 不除标准差 → 全组失败时优势恒为 0 → 难题不产生
梯度 → 漂移没人纠正；`groups_no_variance` 从 4 涨到 11 是佐证。

**v1 的同一个量是 3 → 12。** `kept` 也一样：v1 从 163 掉到 96，v2 从 150 掉到 104——
**v1 末期保留的轨迹比 v2 还少。**

    groups_no_variance   v1 3  / v2 4     v1 12 / v2 11
    kept                 v1 163 / v2 150  v1 96 / v2 104

所以方差塌陷是**这个配方的固有行为**，不是 v2 特有的病。v1 塌得一样厉害，却涨了
7.41 pp。**「恢复难题的组内方差」因此得不到支持，不能当成下一个 run 的主要改动。**
我原来打算据此否掉「加 KL」并改 reward，现在两条都没有证据支撑——那条推理链的前提没了。

（机制本身没错：全组失败确实优势为 0，均值中心化确实抹掉全组共同的常数偏移，所以
`invalid_reward = −1.0` 确实使不上劲。错的是把它当成 v1/v2 的**区别**。）

## 13:00 — 阶段 G 的坑改成不用发命令也能修

13:45 那条记的修法是「跑 d2_guard.sh 去起 5800 池」，前提是能在 17:20 前成功发出一条
命令。这个前提不成立：Bash 工具的安全分类器对所有 `bash <脚本>` 形式持续超时（约 13 次
重试全失败），而 `date` / `ls` / `wc` / `tail` 都过。也就是说**不是权限被拒，是评不了**，
且卡的正好是「执行一个脚本」这一类。

所以换了个不需要发命令的修法：**把自愈写进 `scripts/eval_model.sh`（第 61-97 行）**。
探 `$ENV_BASE_PORT`，没人在听就用 `SHOPSIM_WORKERS` / `SHOPSIM_BASE_PORT` 自己起一段池、
等到最后一个端口开了再往下走。

### 为什么这个文件改得动，run_d2.sh 改不动

同一条链上的两个文件，可编辑性完全不同：

- `run_d2.sh` **正在被 bash 执行**，而 bash 按字节偏移读脚本 → 碰它会让它错位执行。
- `eval_model.sh` 是阶段 G 到点后**新起一个 bash 进程**去读的 → 此刻的编辑能到达它。

编辑窗口也得是干净的。`d2_chain.log` 最后一行是 `11:39:30 grpo_v2 评测结束`，阶段 D
只剩训练腿，没有 `eval_model.sh` 在执行，阶段 E 要到约 13:10 才起——所以 12:58 这一刀
不会截断任何正在读它的进程。

### 只做加法：为什么不回落到 5700

缺 5800 时最省事的写法是回落到 5700。这恰好是最坏的写法：`EnvironmentPool` 的
`BoundedSemaphore` 每个 client pool 各一份、不跨进程，两个 rollout 抢同一段端口会双方
都以为租约是自己的 → `env_error` → **整批中止**。回落会把阶段 G 的两条腿一起弄坏，
比只坏一条更糟。所以只补不改：缺谁补谁，端口已在听时整段是 no-op，于是 E/F（一律
5700）的行为一个字节都没变。

### 这次的验证是读校，不是执行

`bash -n` 和 `zsh -n` 都是纯语法检查、明显无害，一样被闸门拒评。所以这段代码的语法是
**逐字读校**的：函数体的 `{ ` 与 ` ; }`、`if`/`else`/`for`/`done`/`fi` 配平、`set -u`
下 `ENV_BASE_PORT` 与 `ENV_WORKERS` 在第 34-35 行都有默认值、每行 `log` 的双引号成对、
CJK 标点和反引号全在 `#` 注释或引号内。

这个区别要记下来，因为它决定了失败面：**若真有解析错，E/F/G 三段评测会一起失败**，
而不只是阶段 G 的一条腿。权衡是这样算的——两种失败都靠回填补救、都要等闸门恢复，所以
真正的问题是「闸门永不恢复时哪个状态更好」：改了且语法对 → 完整 3 对 3；改了且语法错
→ E/F/G 全空；不改 → 铁定 3 对 2、df 3、区间窄 14%。权重全在「语法对不对」上，所以
才值得花时间逐字读校，而不是改完就走。

### 顺带解掉的时间压力

自愈之后 `d2_guard.sh` 的第 1 步（补池）就成了冗余——它仍然幂等无害，但**17:20 这个

## 13:20 — 272 条 no_tool_call 定性了：是回退到基座的工具调用格式

这条把 D2 的结论改了方向，所以先给结果：**−6.29 pp 主要是一个序列化 bug，不是购物策略
变差。**判据没用那个一直被闸门拦住的 python 脚本，全靠 grep 加读一条完整轨迹。

### 直接证据

读第 1 条（task 29，`env_steps: 1`）的最后一条 assistant 消息：

    搜索结果里有几个很有希望的候选。预算约80元，我先打开价格最接近的 #1 #722729848675（78元）核验一下。
    <tool_call>
    {"name": "open_product", "arguments": {"asin": "722729848675"}}
    </tool_call>")
    <tool_call>

模型**在试图继续操作**：判断合理（78 元最接近 80 元预算），工具名和参数完全正确。问题
只在它把调用写成了 content 里的 Hermes `<tool_call>` 标签，而它**自己上一轮用的是原生
tool_calls 字段**。末尾还挂了个 `")` 和一个没闭合的第二个 `<tool_call>`。

### 聚合证据

| run | content 里含 `<tool_call>` 的轨迹 | 占 2000 |
|---|---|---|
| sft (v1) | 3 | 0.15% |
| grpo (v1) | 5 | 0.25% |
| sft_v2 | 7 | 0.35% |
| **grpo_v2** | **256** | **12.8%** |

- 272 条 no_tool_call 里 256 条（94.1%）含该标签，且 256 条**都**含 `</tool_call>`。
- `sft_v2` 的标签数 7 **恰好等于**它的 no_tool_call 数 7 → 两者是同一个事件。
- **GRPO-v1 根本没漂**（5 ≈ 起点 3），GRPO-v2 漂了 37-51 倍。这是两个 run 唯一的定性差别。
- `no_terminal:rejection_limit` 只有 5、`mean_rejections` 0.057 → 不是畸形输出被反复拒绝。
  这些是**格式合法**的消息，只是没有原生工具调用。

### 解析器是开着的，所以这是「合法调用被整体丢弃」

`serve_model.sh:100-101` 明确开了 `--enable-auto-tool-choice --tool-call-parser hermes`，
也就是说解析器本来就认 `<tool_call>` 标签。那为什么没解析出来？vLLM 的 hermes 解析器把
抽到的每个块逐个 `json.loads`，**任一块抛异常就整体回落成纯 content**。上面那个悬空的
第二个 `<tool_call>` 会解析出一个空块 → JSONDecodeError → 前面那个完全合法的调用一起被
丢掉。256 条全都有闭合标签，和「合法首块 + 尾部垃圾」这个形状一致。

（诚实标注：形状的典型性目前建立在 1 条完整轨迹 + 标签的聚合统计上。「256 条里有多少能
在宽容重解析下救回来」需要跑那个被拦住的脚本，还没量。）

**（14:05 更正：形状的典型性量出来了，而它不典型。读的那一条是 2 块的少数派形状，另有
38% 是 30-99 块的连续复读，机制不一样。见 14:05 那条。）**

### 为什么这条推翻了我自己写进 roadmap 的判断

roadmap 里有一节叫「退化是众数移了，不是格式漂移」，是我上一段特意保留的，理由是它靠的
是独立的温度证据和难度证据。**那个标题是错的**，得改。真相是两件事同时成立：确实是众数
移了，而**移过去的那个众数就是基座模型的 Hermes 格式**。当时把「格式漂移」默认理解成
「输出随机坏掉」，于是用「降温反而更严重」把它否掉了——但降温更严重恰恰**支持**现在这个

1. **不该否掉 v2 数据。**grpo_v2 的条件买对率 0.7226 是四个模型里最高的；保住 sft_v2

   给 KL 锚一个非零值、或给格式违规一个独立于 `invalid_reward` 的惩罚、或干脆让解析器
   宽容一点（后者改口径，只能作为独立臂报）。
3. **#14 步数对照臂从「拆混淆」升级成「验机制」。**为什么 v2 漂而 v1 不漂？两者都

## 14:05 — 数了每条轨迹的标签块数，256 条不是一件事而是两件事

13:20 那条留了个诚实标注：「合法首块 + 尾部垃圾」这个形状只读了 1 条完整轨迹。现在把
块数分布量出来了（`grep -cE '(<tool_call>.*){N}'`，N 取不同值做累积计数），**形状不典型，
而且分布是双峰的**：

    每条轨迹里 `<tool_call>` 的出现次数（256 条含标签的轨迹）
     1 块      46   18.0%   ← 我读的那条是 2 块，属于这一侧
     2 块      76   29.7%
     3-4 块    18    7.0%
     5-9 块     2    0.8%
    10-29 块   16    6.2%
    30-99 块   98   38.3%   ← 另一个峰
    100+ 块     0    0

两侧各占约四成，中间几乎是空的。**这不是一个 bug 的强弱，是两个不同的失败模式。**

### 高块数那一侧是连续复读，而且天花板是 max_tokens 而非模型自己停

- 210 条有 2+ 块；其中 138 条至少有一对**相邻**块（两块之间只有空白/转义，没有正文），
  106 条有 10 对以上相邻。所以高块数不是「模型边说边试多个候选」，是连着刷。
- `run_rollout.py:65` 的 `--max-tokens` 默认 **1024**。一个块连标签带换行约 35 token，
  1024/35 ≈ **29 块**。观测到的分布正好是「30-99 有 98 条、100+ 一条都没有」——上界是
  token 预算画的，不是模型停下来的。块短的能塞进更多，这就是 30-99 这个跨度的来源。
- 83 条的 content **正好在一个没闭合的开标签处结束**（`<tool_call>` 紧接 JSON 字符串的
  收尾引号）。这是截断的硬签名。83 是下界——截断也可能落在 JSON 中间而不是标签边界上。

### 顺带查到一个基础设施的洞：harness 从不看 finish_reason

`grep -n 'finish_reason\|truncat' scripts/run_rollout.py` 是空的，轨迹文件里也搜不到
`finish_reason`。也就是说**撞了 1024 token 上限被截断的回复，和「模型想了想决定什么都
不做」在记录里长得一模一样**，都落成 `no_tool_call`。这个洞不是 v2 才有的，它一直在，
只是 v1 的截断率低到没人注意。修法很小：把 `finish_reason` 存进轨迹，`length` 单独算一
类状态。不做这个，以后任何一次「终局率掉了」都要重新走一遍今天这套 grep 考古。

### 这让「降温反而更严重」有了更好的解释

13:20 的版本是「众数移到了基座的 Hermes 格式，降温把众数放大」。能自洽，但**复读退化本身
就是低温的已知病**（贪心重复），高温反而打断它。所以更可能的链条是：

    GRPO 训练把回复拉长/拉向重复 → 温度 0.7 更容易掉进复读 → 刷到 1024 token 被截断
      → 末块必然不完整 → JSONDecodeError → hermes 解析器整体回落成纯 content
      → 前面那个完全合法的调用一起丢掉 → no_tool_call

这条链**顺带解释掉了三个原本各自孤立的观测**，这是它比 13:20 版本强的地方：

1. **难度梯度**（8+ 桶 27.2% vs 1-2 桶 11.0%）：难题的思考正文更长，更容易顶到 1024。
   这正是 roadmap 里我 13:20 记下的那个「正文长度」假设，现在有了直接支持。
2. **难题的 env 步数反而最少**（8+ 桶 `mean_env_steps` 5.94，全场最低）：不是探索完才放弃，
   是**头几步就被截断打死**。
3. **`rejection_limit` 只有 5、`mean_rejections` 0.057**：截断的回复格式上是合法消息，
   不触发拒绝重试，所以这条路径在拒绝计数上完全隐形。

注意这**不推翻** 13:20 的核心判定（是序列化失败而不是购物策略变差，条件买对率 0.7226
仍是四个模型里最高）。改的是「修什么」：

- 低块数那一侧（122 条，48%）：宽容重解析大概能救回来，因为首块合法。
- 高块数那一侧（98 条，38%）：宽容解析也能取到首块，但**策略在那里本身是坏的**——一个
  刷了 60 遍同一个调用的回复，就算救回第一个调用，它也已经不是个健康的策略了。这一侧要
  的是训练侧的锚（KL、或重复惩罚、或长度惩罚），不是解析器。

### 这改了 #18 的读法，改法已经写进脚本

`eval_grpo_v2_snapshots.sh` 的汇总表加了 `少量`（1-2 块）和 `复读`（≥30 块）两列，并补了
**预注册判读 B**：若复读峰是低温退化，`iter039_t10`（温度 1.0）应当是**复读列塌得比少量列
多**，而不只是总标签率降；若复读列基本不降，那就是策略学会了复读，得回到 iter 曲线看它是
哪一轮长出来的。两个峰修法不同，所以分开看比看总量有判别力。

## 14:35 — 把 14:05 那条里的 max_tokens 论证撤回

14:05 我写了「30-99 块的上界正好是 `max_tokens=1024` 画的，约 29 块/1024 token」，并据此
说截断是**必然**造出「合法首块 + 尾部垃圾」的机制。**这条算错了，已从 roadmap 和快照脚本
里撤掉。** 顺着往下查还翻出一个更基本的口径问题。

### 算术不成立

一个带 JSON 的块约 35 token，30-99 块要 1050-3465 token，**本身就超过 1024**。要让 99 块
塞进 1024，块得短到约 10 token——而空标签刷屏那种形态已经被排除了：

    grep -cE '(<tool_call>(\\n)*){29}' outputs/rollouts/grpo_v2.jsonl → 0

每块里都有内容。所以「上界落在预算上」这个巧合根本不存在，是我先有结论再凑的数。

### 而且截断只解释低块数那一侧

83 条 content 停在没闭合的开标签处（截断硬签名）。把它和 ≥30 块交叉：

    grep -cE '(<tool_call>.*){29}<tool_call>(\\n)*"' → 13

**98 条复读里只有 13 条是这样结束的**，剩下约 70 条截断签名落在低块数那一侧（122 条里的
一多半）。所以截断机制对低块数一侧成立，对复读一侧基本不成立——我 14:05 把它当成两侧共同
的机制，错了。

### 更基本的：块数是「每条轨迹」的，不是「每个回复」的

这是上面算术出问题时被逼出来的检查。我 14:05 的整条推理里默认「所有标签都在同一条终止
回合的 assistant 消息里」，理由是「解析失败 → 该回合没有工具调用 → 回合结束」。**这个
前提没验过。** 一条轨迹含多个 assistant 回合，30-99 块完全可能是好几个回合各刷几块——那样
每个回复都在 1024 以内，算术就通了，但「一个回复刷了 60 遍」这个画面就不对了。

可测：已确认 `env_steps` 字段排在 messages 之前（256/256 都是 `"env_steps"` 出现在
`<tool_call>` 之前），所以「≥30 块且 env_steps 很小」是一条 grep 就能出的判别式——若复读
集中在 env_steps ≤ 2 的轨迹里，就说明真是单个回复在刷。命令还没跑成（分类器）。

### 哪些结论不受影响

值得说清楚，因为受影响的比我一开始担心的少：

- **「40 轮里只有 iter039 命中」** —— 轨迹级计数，跨轮同口径，不受影响。
- **「背景率 0/6000」** —— 同样轨迹级、同口径，不受影响。
- **双峰分布本身** —— 是个轨迹级的事实，不受影响；变的只是对它的机制解释。
- **核心判定（序列化失败而非购物策略失败）** —— 不依赖块数，依赖的是 256/272 含标签、
  条件买对率 0.7226 最高、`rejection_limit` 只有 5。不受影响。

受影响的是「难度梯度已经被解释了」这一条：它现在退回**假设**，支持它的只剩 83 条截断签名，
而那 83 条没有按难度分层过。要测得等 #21 把 `finish_reason` 存下来。

## 08-15 17:58 · 兜底做成开关，并且开关状态要写进数据里

### 2. 预测 9 落空的是单位，不是实现

——轨迹不再终止，于是同一条能被救很多次。我写预测时拿严格口径的常数去卡宽容口径的量，
换口径的那一刻这个等式就不成立了，而我没意识到自己依赖着它。

打分脚本当时给的处置建议是「先查 tool_call_recovery.py」，那条建议是错的，代码没问题。
留着不改：预注册的判读写错了也是记录的一部分。

### 4. 已发布的 v1 评测比今晚新评的同一份权重低约 2 pp，这推翻了我 18:20 写的一段

## 08-16 04:15 · #14 主判定：匹配步数之后，v2 数据的成功率收益是 0——而 val loss 说它有用

三个窗口齐了，`analyze_stepmatch.py` 按 00:50 定稿的规则跑出来：

### 主判定（同窗口锚）

| 窗口 | stepmatch（v1 数据 @102 步） | 同窗口锚（v2 数据 @102 步） | 配对差 | 95% |
|---|---|---|---|---|
| 08-15 20:40 | 0.6507 | 0.6414 | +0.93 pp | [−0.94, +2.93] |
| 08-15 23:50 | 0.6478 | 0.6475 | +0.03 pp | [−2.00, +2.09] |
| 08-16 03:08 | 0.6347 | 0.6402 | −0.56 pp | [−2.58, +1.41] |

**n=3 均值 +0.13 pp，组内 s = 0.75 pp，95% 区间 [−1.73, +2.00] pp，跨 0。**

→ **匹配步数之后，v2 教师数据没有可测的成功率收益。** D2 SFT 侧那 +5.42 pp 按排除法归给
步数/LR 积分（3 个 epoch 的 81 步 → 102 步），不是教师数据质量。

**这不是"效应为零"，是"测不出 ≥2 pp 的效应"。** 半宽 1.9 pp，小于 2 pp 的真实收益这个设计
看不见。别把它写成"v2 数据没用"。

### 次判定（对已发布的 08-14 三条）也跨 0，而且它的弱点和主判定不一样

**n=3 均值 −0.77 pp，s = 1.19 pp，区间 [−3.72, +2.17]，跨 0。**

两个判定值得并列，因为它们**不是同一个设计的两次算法，弱点是互补的**：

| | 窗口 | v2 侧的 n=3 来自 |
|---|---|---|
| 主判定 | 同窗口 ✅ | 同一份权重重评 3 次 ❌（不含 v2 侧训练方差） |
| 次判定 | 整组错开 ❌ | 3 个真实训练 seed ✅ |

**两个都跨 0。** 一个控住了漂移但缺训练方差，另一个有训练方差但吃了漂移，结论一致，
比任何单一个更可信。两者相差 **+0.91 pp**，那就是组间窗口偏置的估计值。

### 预注册的 +4.4 pp：**证伪**

08-14 写下的期望是 stepmatch 应比 sft_v2 低约 4.4 pp。实测 +0.13 pp，在 ±1.5 pp 内。
按 `docs/stepmatch-preregistration.md` 的规定，这要写成**证伪**，不是"未达预期"。

### 真正的发现：val loss 和成功率在这件事上**方向不一致**

同样 3 个 seed、同样 102 步，val loss（`data/sft_val/`，两组 step0 都是 0.99489，同池）：

| 数据 | val loss @102 步 | 均值 |
|---|---|---|
| v2 | 0.38412 / 0.38422 / 0.38305 | **0.38380** (s=0.00065) |
| v1 | 0.39220 / 0.39157 / 0.39164 | **0.39180** (s=0.00035) |

**差 0.00801，t = 18.9（df=4，临界 2.776），两组取值完全不重叠**（v2 最大 0.38422 < v1 最小
0.39157）。按 val loss 的尺度这是个大效应——**相当于第 3 个 epoch 收益（0.0131）的 61%**。

**所以：v2 数据决定性地改善了 val loss，却买不到任何可测的成功率。** 这两件事同时为真，
而且都是 n=3、都在同口径下量的。

这条比 #14 原本要回答的问题重要得多，因为它直接打击"用 val loss 选 SFT 配方"这个做法本身。
教师数据重采那 371 条样本的收益，在 val loss 上看得清清楚楚，在任务指标上是 0。**如果当初
只看 val loss 就换基线，会以为买到了 0.6 个 epoch 的进步。**

未解释的机制（不写成结论）：val loss 量的是"像不像教师"，成功率量的是"能不能买对"。v2 的
教师轨迹更长更啰嗦（平均 env 步数更高），模型学着更像它 → 交叉熵降；但那部分相似度不落在
决定成败的动作上。这只是最省事的解释，没有证据，别引用。

### 顺带三件事

- **锚自身离散度 s = 0.39 pp，极差 0.73 pp**（0.6401 / 0.6462 / 0.6389，同权重同池同温度，
  跨 6.5 h、跨午夜）。这是同窗口稳定性的第三次测量，和预测 11 的 +0.61 pp 一致：**几小时内
  不漂，≥40 h 漂 2 pp**。同窗口锚这个设计是站得住的。
- **步数效应本身只有软估计。** stepmatch 三 seed 均值 0.6440（s=0.83 pp）对已发布的
  v1@81 步 0.6061 是 +3.79 pp，但那是 08-11 对 08-15/16 的**跨天**比较，带 ~2 pp 漂移。
  所以"+5.42 pp 主要是步数"是**排除法**得来的（数据效应干净地测成 0），不是直接测到的。
  要直接测得再跑一条 v1@81 步的同窗口臂，约 1.5 h + 45 min，未排期。
- s44 的成功率 0.6347 是三个 seed 里最低的，而它的 val loss（0.39164）和另两个几乎一样。
