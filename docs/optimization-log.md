### 卡的分配（与计划的偏差，必须记进结论）

计划里 S4 假定 7 张卡。实际 E1 评测占着 GPU 1-2（它在两张卡上交替预热下一个模型），
所以 **S4 用 GPU 3-7 五张**。串行等 E1 跑完再用 7 卡要 6.1 h，并行只要
max(3.8 h, ~3.3 h)。代价是步数变了：

| 卡数 | per_rank = 648/卡 | steps/epoch = per_rank//4 | 3 epoch 共 |
|---|---|---|---|
| 6（已发布的 SFT） | 108 | 27 | 81 |
| 7 | 92 | 23 | 69 |
| **5（本次 S4）** | **129** | **32** | **96** |

S4 内部的三处比较（e3 / e2 / e3-epoch2）共用同一个 world_size，自身自洽；且 S1 修好
之后 val loss 已经与卡数无关。但 **S4 的 val loss 与已发布 SFT 的 0.39249 不可直接比**
——后者是在丢掉 3 条最长验证样本的口径下量的（见下）。

**更要紧的一条：`sft` vs `sft_e3` 这一对不能当作「重训的 run 间方差」来读。** 卡数变了
就等于 optimizer 的 global batch 变了——`grad_accum 4 × 5 卡 = 20 批`，而已发布的 SFT
是 `4 × 6 = 24 批`。所以那一对同时混了「重训」和「批大小」两件事，只能当参考锚。
S4 真正要回答的「第 3 个 epoch 值不值」完全落在 5 卡这一族内部，不受影响。

**推论：R1 的两个 seed 必须用和已发布 seed 42 相同的 6 张训练卡**
（`GPU_VLLM=1, GPUS=2,3,4,5,6,7`，即 `train_grpo.sh` 的默认值）。同样的道理：4 卡的
global batch 是 8 批而 6 卡是 12 批，若 seed 43 用 4 卡、seed 44 用 6 卡，卡数就和 seed
混在一起，恰好毁掉这个实验要量的 run 间方差。因此 R1 只能等 E2 让出 GPU 1-2，不能为了
填满空闲卡而改卡数。

### S1/S2/S3：train_sft.py 三处修复

**S1（错）** `evaluate()` 之前用 `shard()` 切验证集。`shard()` 为了对齐 FSDP 的集合
通信把各 rank 截到等长，丢掉尾部 `len(batches) % world_size` 批。训练侧丢一点无所谓
（每个 epoch 重新 shuffle，长期每条都会被采到），验证侧是致命的：
`token_budget_batches` 先按长度排序且 val 从不 shuffle，所以每个 epoch 丢的**永远是
同样那几条最长的样本**，而丢几条**取决于卡数**——6 卡丢 3 条、7 卡丢 6 条、8 卡丢 7 条。
已发布的 0.39249 实际是 295 条样本上的数，且换卡数就变。

修法：新增模块级 `val_rounds()`，按 `batches[rank::world_size]` 分，短的 rank 用
**零权重**重复自己的第一批补齐轮数。轮数对所有 rank 相同（不然 FSDP 卡死在 all-gather），
每条样本恰好计一次权重 1.0。

**S2（缺）** val loss 只进内存 `history`，中途崩了就全丢；且没有 epoch 0 的基线点，
「第 3 个 epoch 只降 0.0032」这类判断没有起点可依。修法：`emit()` 每条记录即时追加到
`train_log.jsonl`；训练前先量一次记为 epoch 0；`metadata.json` 里把含糊的 `final`
拆成 `final_train` + `val_curve`。

**S3（错）** `steps_per_epoch` 用 `math.ceil`，而训练循环是
`range(0, per_rank - grad_accum + 1, grad_accum)`，只走完整的 grad_accum 组，实际步数
恒为 `per_rank // grad_accum`。ceil 会让 `total_steps` 超过所有 epoch 加起来能走的步数，
于是 while 多跑一个残 epoch 去补，余弦在残 epoch 中途才退到 0，`--save-each-epoch`
还会多写一个目录。之前没暴露纯属整除的巧合：6 卡 per_rank=108、7 卡 92 都被 4 整除；
8 卡 per_rank=81 就会踩（ceil 21 vs floor 20 → total 63 而 3 个 epoch 只有 60 步）。
顺带补了 `steps_per_epoch == 0` 的守卫——那种情况下 while 只看 `step < total_steps`，
会永远转下去。

三处各配了回归测试，`tests/test_train_sft.py` 26 条，全套 389 passed / 3 skipped。为了让
逻辑可测，`val_rounds` / `steps_in_epoch` 从 `main()` 的闭包里提到模块级。

**冒烟**（5 卡，`--limit 48 --max-train-steps 2`）：epoch 0 量到 val 1.024，1 步后 0.798，
末步 lr 退到 0，`metadata.json` 里 `val_curve` 两点齐全、`final` 已消失。

先在 2 卡上试过一次，rank0 在 epoch-0 验证之后退出 1，当时 GPU 4 已到 79.9/80 GB。
最可能是 2 卡下 FSDP 只把优化器状态切成两份（约 40 GB/卡，6 卡时约 13 GB）导致的 OOM，
**但当时用了 `| tail -30`，原始异常被截掉了，这个归因是推断而非实证。** 换到 5 卡即通过，
而 5 卡正是 S4 要用的配置，所以没有继续追这条。

顺带核了两件与改动相邻的事：`evaluate()` 结束时会 `model.train()` 回去
（`train_sft.py:376`），且 Qwen2.5 的 `attention_dropout=0.0`，所以我新加的「训练前先量
一次」不会改变 epoch 1 的训练行为；`save()` 只 gather 一份副本转 bf16 写盘、两端各一道
barrier，中途存不动活模型。`--save-each-epoch` 的 `if ... and not stop` 保证最后一个
epoch 不重复存——而这一条恰好依赖 S3 的 floor 口径，ceil 时会多进一个残 epoch、多写一个
`epoch3/`。

### 「第 3 个 epoch 只降 0.0032」的出处，以及它错在哪

那个数来自已发布 run 的控制台日志 `outputs/logs/sft_full.log`：

```
[15:06:59] epoch 1 验证 loss 0.44066
[15:40:33] epoch 2 验证 loss 0.39567
[16:14:13] epoch 3 验证 loss 0.39249
```

0.39567 − 0.39249 = 0.00318。**但这三个数都是在 S1 的 bug 下量的**（日志打印「验证样本
298」，实际只算了 295 条——`shard()` 把 6 卡截到等长，丢掉 3 条最长的）。

为了把 S1 的影响单独摘出来，拿**已发布的那份权重**用修好的代码在完整 298 条上重测了一次
（GPU2 空着，单卡一次前向，复用 S2 新加的「训练前先量一次」，没写新代码）：

| 口径 | val_loss |
|---|---|
| 已发布：`shard()`，295 条 | 0.39249 |
| 修复后：`val_rounds()`，298 条 | **0.39379** |
| **S1 造成的偏乐观** | **+0.00130** |

方向与机制一致：丢掉的是最长、loss 最高的样本，丢了报出来的就偏低。

**值得停下来看一眼的对照：S1 这个测量误差（0.0013）是「第 3 个 epoch 真实收益」
（0.0003）的 4 倍。** 也就是说，原本用来判断「第 3 个 epoch 值不值」的那个 0.0032，
是在一把量不准的尺子上读的，而尺子的误差比要测的东西还大。

顺带把两个 run 的绝对值也校平了。同在 298 条口径下：已发布 sft 0.39379 vs S4 sft_e3
0.38993，S4 低 0.00386。这**不能**归给「重训的 run 间方差」——5 卡走 96 步、6 卡只走
81 步，optimizer step 数不同（见上文卡数那节）。两个 run 的数据完全一致
（1776 训练 / 298 验证，sha256 相同），差的就是步数。

（第一次跑探针漏传了 `--validation`，白跑一次只写到 `/tmp`，没碰任何产物；不能用
`--limit` 抄近路，它会连验证集一起截断。）

| iter039 vs iter019 | +1.70 pp | [-0.35, +3.92] | 否 |

k=8 下各自成功率：iter019 65.69%、iter034 69.27%、iter039 67.72%（k=4 时分别是
65.56 / 68.81 / 67.91，移动都在噪声内）。

**跑之前写在 `topup_k8.sh` 头部的两条预测都中了**：iter034 vs iter039 的 0.60 pp 差
「大概率仍判并列」——确实不显著；iter019 vs iter034 的 2.64 pp「可能分得出」——确实分出来了。

### E1 的结论

1. **没有提前见顶。** iter034 显著优于 iter019（+2.91 pp，区间不跨 0）。这正是 E1 设计时
   说这套配置「能回答」的问题，答案是训练在 iter019 之后还在涨，不是早就到顶后面白跑。
2. **iter034 与 iter039 分不出。** 没有证据支持把已发布的 iter039 换成别的检查点。
   原始担心的「iter039 是最后一个而不是最好的一个」，在这个分辨率下测不出来——
   而按预注册，测不出来就是结论，不加采样、不挑。
3. 附带：平均 env_steps 从 sft 的 14.63 单调降到 iter014 的 9.78。GRPO 同时在提高成功率
   和降低步数。

配对区间半宽约 ±1.9 pp，比 vs-sft 那一列的 ±4 pp 窄一半多——同血缘模型在同一批题上高度
相关，配对差值的方差小。这正是当初决定「只补三个模型、不补 sft 基线」的依据：补基线是为了
窄化 vs-sft 那一列，而并列要解决的问题根本不在那一列上。

**给训练循环接 in-loop val 的建议因此要改口径。** 原计划的动机是「iter039 可能不是最好的，
需要在训练中选」。E1 的结果不支持这个动机：末尾几个检查点彼此测不出差异，选不选都一样。
in-loop val 真正的价值退化为「早停省算力」——iter019 之后还在涨，所以连早停也省不了多少。
这条建议的优先级应当下调，除非未来的 run 表现出明显的过训退化。

## 2026-08-13 06:52 — S4 结束，「2 vs 3 epoch」的对照被之前搞错了

`sft_e2`（2 epoch，5 卡 64 步）跑完，exit=0，lr 末步 0.0。

| 模型 | 口径 | val_loss |
|---|---|---|
| `sft_e2` | 2 epoch，余弦在 64 步内退到 0 | **0.40310** |
| `sft_e3` @ epoch 2 | 同样看过 2 遍数据，余弦只走到 2/3（lr≈2.5e-6） | 0.39023 |
| `sft_e3` @ epoch 3 | 3 epoch 退火完 | 0.38993 |

健全性检查：两个 run 在 epoch 1 的 val 几乎相同（0.42637 vs 0.42674）——同 seed、同数据、
同卡数，只有 LR 计划不同，符合预期。

**之前的对照搞错了对象。** 「第 3 个 epoch 只降 0.0032」（修正口径后是 0.0003）比的是
**同一条余弦曲线的中点和终点**。但「该训 2 轮还是 3 轮」问的是两个**各自退火完整**的 run
谁更好——那是 0.40310 vs 0.38993，**差 0.0131，比原先那个数大 40 倍**。

也就是说，到目前为止在 val loss 上，**第 3 个 epoch 是值的**，与最初的猜测相反。
这正是 S4 设计成「独立的 2-epoch run」+「3-epoch run 的中点」两份权重的原因；只跑其中
一份都会得出错的结论。

反直觉的一点：退火完的 2-epoch（0.40310）反而比没退火的中点（0.39023）差 0.013。
合理解释是 64 步下模型还欠拟合，提早把 LR 退到 0 等于锁在一个更差的点上——总 LR 积分
更大的那个走得更远。注意这也意味着 `eval_sft_variants.sh` 头部说的「sft_e3/epoch2 vs
sft_e2 的差就是退火的贡献」需要修正措辞：两者的差**不只是**退火，还有「同样步数下累积
LR 不同」这一项，二者在这个设计里分不开。

**但判定仍以任务成功率为准，不以 val loss 为准**——这条写在 E2 脚本头部，理由是
val loss 低不等于成功率高，而报告里报的是成功率。0.0131 的 val loss 差能不能在 ±3.2 pp
的分辨率下看见，是 E2 要回答的。

## 2026-08-13 08:06 — E2 出结论：问题问错了，真正起作用的不是 epoch 数

四份 SFT 权重，各 200 题 × k=4 = 800 回合。以已发布的 `sft` 为基线：

| 模型 | 成功率 | 95% CI | vs sft | 配对区间 |
|---|---|---|---|---|
| sft（已发布，6 卡 81 步） | 58.50% | [53.05, 63.83] | （基线） | |
| sft_e2（5 卡 64 步，退火完） | 54.00% | [48.19, 59.72] | **−4.23** | [−7.78, −0.42] |
| sft_e3_ep2（5 卡 64 步，余弦未走完） | 61.22% | [55.23, 66.84] | +2.44 | [−0.77, +5.64] |
| sft_e3（5 卡 96 步，退火完） | 62.07% | [56.25, 67.47] | +3.29 | [−0.04, +6.37] |

按预注册的并列规则（前两名差 > 3 pp 才补 k=8）：sft_e3 与 sft_e3_ep2 差 0.85 pp，
**判为并列，不补采**。不报排名。

卫生：四份都 0 基础设施失败，非 done 的只有 `rejection_limit`（1~5 条）和 `no_tool_call`
（0~3 条），这两个本来就该算失败。没有 `empty_response`。

### 但上表的基线选错了对象

`sft` 是 6 卡，其余三份是 5 卡。「vs sft」那一列同时混着 epoch 数、退火、和卡数
（global batch 24 批 vs 20 批）三件事。真正干净的比较全在 5 卡族内部——同 seed、同数据、
同卡数。这三份两两配对（正数 = 前者更好，配对题数均 195）：

| 配对 | Δ | 95% CI | 显著 | 这一对唯一变动的是 |
|---|---|---|---|---|
| sft_e3_ep2 vs sft_e2 | **+6.71 pp** | [+3.68, +10.00] | **是** | **只有余弦长度** |
| sft_e3 vs sft_e3_ep2 | +0.85 pp | [−2.56, +4.15] | 否 | 多走的第 3 个 epoch |
| sft_e3 vs sft_e2 | +7.56 pp | [+3.97, +11.03] | 是 | 上面两项之和 |

**第一行是整晚控制得最干净的一次比较。** `sft_e3_ep2` 和 `sft_e2` 都是 64 个 optimizer
step、同一份数据、同一个 seed、同样 5 卡，连数据顺序都一样；唯一的差别是余弦按 96 步
铺还是按 64 步铺——即 step 64 时 LR 是 2.5e-6 还是 0。差 6.71 pp，区间不跨 0。

第二行说：多走的那 32 步（整个第 3 个 epoch）买到的东西**测不出来**。

### 结论：「第 3 个 epoch 值不值」这个问法本身有问题

7.56 pp 的总差里，6.71 pp 归给 LR 计划，剩下 0.85 pp 归给多走的一个 epoch 而且测不出。
也就是说——

- **不是「3 个 epoch 比 2 个好」，而是「别在模型还欠拟合时就把 LR 退到 0」。**
- 想省三分之一算力是可行的：按 3 epoch 的长度设余弦、只训 2 epoch 就停
  （这正是 `sft_e3_ep2` 的口径，61.54% vs `sft_e3` 的 62.39%，并列）。省下 32 步，
  代价在当前分辨率下测不出来。

这和 06:52 记的 val loss 排序完全一致（0.40310 / 0.39023 / 0.38993），两套互相独立的
测量给出同一个次序。E2 头部问的「0.0131 的 val loss 差能不能在 ±3.2 pp 下看见」——
能，而且很清楚。

### 三条限制，别把上面的话说过头

1. **并列不等于相等。** `sft_e3 vs sft_e3_ep2` 的区间是 [−2.56, +4.15]，一个真实存在的
   3 pp 差异完全能藏在里面。结论只是「在 n=200、k=4 这个分辨率下测不出」。
2. **单 seed。** SFT 的 run 间方差从没量过（R1 量的是 GRPO 的）。`sft_e2` 和
   `sft_e3_ep2` 不是同一条轨迹的分叉，从第 1 步起 LR 就不同，所以「LR 计划的效应」和
   「这两个 run 恰好差了这么多」分不开。支持前者的旁证是 val loss 独立给出同向结果。
3. **`sft_e3` vs 已发布 `sft` 的 +3.29 pp 区间是 [−0.04, +6.37]，只差一点点没跨 0，
   且混着卡数。** 不能当结论，但值得记成一个待查问题：已发布的 SFT 基线有可能比同配方
   多走步数能达到的水平低约 3 pp。若属实，GRPO 那个 +7.41 pp 就是踩着一个偏弱的基线量的。
   要证伪只能用 6 卡重训一次 3-epoch SFT，本轮不做。

### 11:15 顺带看到：`shard()` 的余数在**训练侧**也在丢东西
